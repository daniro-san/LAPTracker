## Should-fix

### S1. A manual `/api/snapshot` before the event's `before_at` completes the coming Saturday's phase, and the tick then skips the real run

- `app/api/snapshot/route.ts:24` → `lib/schedule.ts:110-113` (`currentEvent`), `lib/repo/events.ts:86` (`duePhases` skips any phase with a row).
- Plan: §3.1 "Manual fallback: 'Run BEFORE/AFTER now' … the real backup if Actions is late or down"; §4 "Never run a full test on event day. Dry runs happen midweek"; D20 kept `test=1` so "the weekday dry run cannot complete the coming Saturday's BEFORE"; D21 removed `test=1` ("a dry run is a rehearsal") and added no replacement guard.
- Code: `currentEvent` picks the Saturday nearest to `now`. From Wednesday 12:00 UTC on, that is the coming Saturday (probe: Sun–Tue → last Saturday, Wed–Sun → 2026-11-07). A press on Wednesday creates the real event row, runs BEFORE on it and stores it `complete` with Wednesday data. On Saturday `duePhases` finds the row and never runs BEFORE; AFTER runs normally. The week's delta is Wednesday→Saturday and nothing says so except the `started` time in the admin message.
- Fix: in `executeSnapshot` or the route, refuse with 409 `snapshot_not_due` when `ctx.now() < req.event.beforeAt`, `force` included (an early AFTER on Saturday stays allowed because it is after `before_at`). One route test: Wednesday press → 409, no row, no `/v1` call.

### S2. A 429 mid-run gives a `partial` snapshot with empty `stale` and `failed`; the public message names nobody and the admin message does not list the alliances without a row

- Plan: Phase 6 partial template "⚠️ … but 2 alliances came back with old data (ABC, DEF). No change is shown for them"; admin message "per-alliance failures with HTTP codes"; §4 "a re-run fetches only alliances without a row" (the admin has to know which).
- Code (probe, 429 on the 8th alliance call): `status: partial, error: 'quota exhausted (429)', stale: [], failed: []`. Public: `⚠️ Saturday ledger updated (before the event), but 0 alliances came back with old data (). No change is shown for them.` Admin: the error line only; the 13 alliances with no row are not named. `runResponse` has the same gap.
- Fix: in `finish`, add every id in `ids` without a row to `failed` as `{ unionId, tag (from config), error: \`not fetched: ${error}\` }`. Both templates and the JSON then carry them with no new field. Extend `lib/collector.test.ts` "stops on a 429 mid-run" to assert `failed` lists exactly the ids without a row.

### S3. An AFTER run on an event whose `alliance_ids` is empty spends the quota call and records `failed` with `error: null`

- `lib/collector.ts:118-126` (`allianceIds`), `:320-321` (quota check runs before the empty list is noticed), `:260-265` (`ok.length === 0` → `failed`).
- Plan: §3.4 / Phase 3 "the AFTER run uses the event's copy"; §6 `snapshots.error` "one line". In the plan the BEFORE run created the event, so AFTER-without-BEFORE was `no-event`. Reachable on any Saturday where the tick was dead for BEFORE's 45-min window and alive for AFTER's. `app/api/snapshot/route.test.ts:143` relies on this behaviour ("the first AFTER failed (no alliances on the event)").
- Fix: in `runSnapshot`, after `allianceIds`, when `ids.length === 0` return `finish(run, ids, phase, "no alliance list on the event: BEFORE has not run")` before `checkQuota` (0 calls, status `failed`, reason in the row and the admin message). The existing auth-matrix test keeps passing (a failed row is re-runnable).

## Notes

- N1. **Verdict quota line undercounts when the run's last `/v1` attempt fails and the internal fallback fills the row** — `lib/collector.ts:99-103` (`lowestRemaining` is the lowest `remaining` _seen_), `lib/rehearsal.ts:88-91`. A 502/503/504 body carries no quota object, so attempts after the last successful response are invisible. Probe: last alliance 503, fallback live → `complete`, `calls_used 21`, drop `900 − 881 + 1 = 20` → `❌ calls_used ≠ quota drop: 21 ≠ 20` on a run that was fine. Needs every retry of the last alliance to fail and the fallback to succeed; rare. An exact fix needs a per-run count of attempts without a quota object (new column); cheapest mitigation is a verdict line that says "n /v1 attempts returned no quota" when `run_logs` has a `v1.fetch` warn line for that run.

Under a sustained stream (DB down, a request every few minutes) the owner gets one message total. Two instances reading `last` together both post. Fix if wanted: a claimed alert row like `claimQuotaCheck` (conditional update on a single-row table).

## What I checked and found correct

1. **Complete with a stale row — `/v1`, fallback, re-run.** `is_fresh` is computed once per row at storage time from `deps.now()` and the response's `updated_at` (`lib/collector.ts:175`, `lib/compute.ts:14-16`, `≤ 20 min`, null → stale); the internal fallback goes through the same `dataRow` (`:227`). `finish` gives `complete` only when every id has a row with `error === null` and `isFresh` (`:260-265`); a stale row is never re-fetched by a plain re-run (`:325-329`), so a snapshot with one can only become `complete` through `force`, which clears the rows first (`:114`). The crash path closes the row as `failed` (`lib/run.ts:45-75`). Pinned by `lib/freshness.test.ts` 1–4 and the collector tests. See N8 for the re-run timing caveat.
2. **Deltas.** `delta()` returns null when either side is not fresh or any total is null (`lib/compute.ts:28-36`, property test "is null whenever either side is stale"); `seriesDeltas` applies the same rule (`:109-125`). No read model or route computes a delta yet; `getEventDetail` returns `total_power`/`total_kills` and `power_board`/`kills_board` as separate fields (`lib/queries/events.ts:52-67`) and nothing combines them. Nothing enforces the rule in Session 6's UI except using these functions — recorded in the adjustments.
3. **AFTER uses the event's copy.** `allianceIds` returns `event.allianceIds` for `after` and never reads config (`lib/collector.ts:118-126`, mutation "AFTER reads the config" killed in 03); `errorRow` reads config for labels only (`:182`). `finish` filters stored rows by the event's ids (`:255-257`), so a BEFORE re-run after a config change cannot leave foreign rows in the status. The empty-copy case is S3.
4. **`MAX_UPSTREAM_CALLS`.** `attemptHook` is the only increment (`lib/collector.ts:71-78`, one `run.calls++`), passed to `fetchQuota` (`:132`) and every `fetchAlliance` (`:211`); the adapter calls it before every attempt, retries included, before the concurrency slot is taken (`lib/sources/v1.ts:68`). The cap check is `>=` and throws before the request; `CallCapError` sets `capped` and aborts with no fallback (`:218-223`); status `failed` (`:261`). `quotaReport` and `GET /api/quota` call `fetchQuota` outside a run, which the per-run counter does not cover by design. Tests: "aborts at MAX_UPSTREAM_CALLS" (120 calls, 119 rows), "reports every attempt to onAttempt".
5. **Internal API boundary.** `lib/sources/internal.ts` has two GETs with `User-Agent` and `Accept` only (`:33-45`); no refresh path, no POST, no Origin/Referer/Cookie; `fetch` sends no cookies. Used only by `fetchBoard` (`lib/collector.ts:148-156`) and the per-alliance fallback (`:225`). The grep test `lib/sources/no-upstream-literals.test.ts` and `internal.test.ts` "sends a plain GET…" cover it; `.claude/rules/collector.md` states the rule.
6. **Logger.** Every line is one INSERT in try/catch (`lib/logger.ts:48-61`); a failed insert increments a counter and mirrors `console.error` once per run; nothing is rethrown; the cap is per logger instance with `log.capped` as the 400th row (`:63-81`). It imports `./redact` and a type from `./repo/run-logs` only; nothing it calls calls it back; `recordAppError` is never reached from a logger failure. A dead DB delays a run by the insert latency of the awaited lines, which the plan's "writes synchronously" accepts (N5 for the unbounded `shutdown`). Tests: cap, repo-throws-run-completes (failedWrites > 20), redaction of `EDIT_PIN`.
7. **Exception cap.** `app_errors` is trimmed to the newest 500 on every insert (`lib/repo/app-errors.ts:16-26`), so no burst can grow the table; the 1/s limiter is per instance as the plan says (`lib/app-errors.ts:10-12`); the logger has no batch API, so no aggregate can land as one line past the 400 cap. The alert cadence is N2.

AND started_at = ? RETURNING` (`lib/repo/snapshots.ts:20-47`); a lost race returns null → `RunRefusedError('running')` → 409 (`lib/collector.ts:112-113`, `lib/run.ts:37-41`).
