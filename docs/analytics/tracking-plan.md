# Tracking plan (D115)

What we send to PostHog (project 741657, US cloud, D77), which product question each event answers, and the insights and funnels to build from it. An event that answers no question here is not added. `lib/analytics/events.test.ts` fails `pnpm check` if an event, a desk feature or a desk action in the code is missing from this page, and if a table's Event column here names an event that is no longer in the code's event lists (`ANALYTICS_EVENTS` in `lib/analytics/events.ts`, `ServerEvents` in `lib/analytics/server.ts`).

## Rules for every event

- No member values, no names, no free text, no roster private fields (CLAUDE.md, D71, D76), no Discord id, no email, no ids beyond the pseudonymous person.
- Properties are enums from a closed list, booleans or counts. In the browser, `lib/analytics/events.ts` types every property as a closed list of words, and `events.test.ts` fails if one could take any string or a number. On the server, `lib/analytics/server.ts` is the closed list (`DESK_FEATURES`, `DESK_ACTIONS`); `server.test.ts` and `lib/private/desk-action.test.ts` check the payloads.
- `before_send` (`lib/analytics/sanitise.ts`) adds `area` (`public`, `workspace`, `admin`), `workspace` (the slug) and `section` (the tab) from the event's own path, and cuts query strings and hashes from every URL.
- **Which alliance (issue 452).** Every event from a workspace carries `workspace` (the slug, e.g. `ogs`) and `alliance` (the alliance's public tag, e.g. `OGs`, from `config/alliances.ts`). Neither is personal data; member names, uids and Discord ids are still never sent. They are plain event properties, not PostHog groups (a paid add-on), so any insight can filter or break down by them.
  - Browser: `AnalyticsPerson` registers both as super properties on desk and board page loads (`registerWorkspace` in `lib/analytics/events.ts`), so page views, `ws_*` events and exceptions carry them. Replay batches (`$snapshot`) get no super properties from posthog-js, only `workspace` from the path; a recording is found by alliance through its session's other events. Sign-out unregisters them before `reset`. A client-side visit to a page outside `/w/<slug>` unregisters them (`followPath`), and `before_send` removes both from any event outside `/w/<slug>`, so public and `/admin` events never carry them. A page load that started on a public page never registers them, as it never identifies: cookieless loads stay untouched.
  - Server: `ws_action` always; `$exception` when the route is under `/w/[slug]` or `/api/w/[slug]` and the slug names a workspace (looked up after the response); `$ai_generation` from the notice and thanks writing helps and from Discord Translate (the workspace found by the Discord server's guild id); `discord_command_used` from a workspace's Discord server (owner, 2026-11-19).
- People first (D75): nothing here ranks officers or members. Events count use of the desk, not who did the most. No insight below breaks down by person.

## Who is counted

| Where the page load starts                                                         | Distinct id                                                                                                      | Person profile                                      | Replay                           |
| ---------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------- | --------------------------------------------------- | -------------------------------- |
| A public page, visitor has not answered the analytics question or said "No thanks" | PostHog's cookieless daily hash (IP, user agent, host, a daily salt PostHog deletes)                             | none                                                | none                             |
| A public page, visitor said "Allow" on this device                                 | PostHog's own id, kept in its cookie and local storage                                                           | none                                                | 25 % of page loads (D77 masking) |
| `/w/<slug>` (desk or board), signed in                                             | `ws_` + 32 hex: HMAC of the workspace user id under a key derived from `CRON_SECRET` (`lib/analytics/person.ts`) | `tier` (`officer` or `member`) and `workspace` only | yes, masked (D77)                |
| `/admin`, or `/w` signed out                                                       | a random id for this page load                                                                                   | none                                                | yes, masked (D77)                |

Daily unique visitors on public pages are real (one hash per visitor per day, or one id for those who allowed the cookie). Desk and board users are real across days and devices. Sign-out calls `reset`. `identify` does nothing on a cookieless page load.

## Desk actions (server, every write that went through)

Properties: `feature` and `action`, `tier` = `officer`, `area` = `workspace`, `workspace` and `alliance`. A refused write (409, 400, signed out) is not counted. A write repeated with the same request id after a lost answer (D100) is counted again: the lib functions answer a replay exactly like the first write, so the route cannot tell them apart. Funnels (issue 486). No person or property links the way in to the setup: the request is sent by a visitor with no id, the approval by the owner, a signed-out `/w` page gets a new random id on every page load (the Discord sign-in reloads it), and nothing before the workspace exists carries `workspace`. So the way in is counts, and the setup starts at `ws_action` `workspace` / `create`. The setup steps use the server's `ws_action`, not the browser events: it counts every write that went through, whether or not the tab closed, an ad blocker ran or the visitor allowed the cookie. `ws_bot_installed` is no setup step: an invite's "finish" marks the bot seen, so Check never finds it for the first time in an invited alliance. Every setup insight leaves out the own alliance (`workspace != ogs`) and test workspaces.

- **Way in** — Trends, weekly total count of `ws_access_requested`, `admin_workspace_approved`, `ws_invite_opened`, `ws_invite_completed` and `ws_action` `workspace` / `create`, side by side, with the ratio `ws_invite_completed` ÷ `ws_invite_opened` (counts, not a funnel); `ws_access_requested` broken down by `roster_match`.
- **Setup per alliance** — Funnel aggregated by `properties.workspace` (not by person: different officers do different steps), ordered, within 30 days: `ws_action` `workspace` / `create` → `discord` / `save` (a webhook) → `roll_call` / `mark` → `notice_publish` / `publish`. The tracker key is optional (D134), so it is no step.
- **Setup table** — one row per workspace: when it was made and, for each of the key saved (`tracker_key` / `save`, and the last `ws_key_saved` `state`), a webhook (`discord` / `save`), a roll call added and marked, a notice added and published, the first time and the days since the workspace was made. Empty cells are where each alliance is stuck. The admin features' own count is `ws_action` `features`; `admin_feature_changed` adds which switch and whether it is on.
- **Retention per alliance** — officers: `ws_action` → `ws_action`, weekly, breakdown `alliance`; members: `ws_sign_in_completed` (tier member) → `$pageview` with `section = board`, weekly, breakdown `alliance`.

Insights:

- **Tabs opened** — Trends, `$pageview` with `area = workspace`, breakdown `section`, weekly, total and unique users.
- **Screenshot funnel** — Funnel: `ws_screenshot_sent` → `ws_draft_saved` (or `ws_action` `screenshot_draft` / `save`), within 1 day; breakdown `kind`. A second funnel ends on `ws_draft_discarded`; `ws_screenshot_failed` trends by `stage` show where reading breaks.
- **Notice funnel** — Funnel: `ws_action` `notice` / `add` → `ws_notice_translated` → `ws_notice_published`, within 7 days.
- **Paste and read** — Trends, `ws_updates_pasted` and `ws_text_read` by `outcome`.
- **Thanks** — Trends, `ws_thanks_shared` by `to`, weekly; funnel `ws_action` `thanks` / `draft` → `ws_thanks_shared`.
- **Hellos (issue 516)** — Trends, `ws_action` `follow_up` / `record`, weekly, breakdown `from` (read a missing `from` as `follow_up`) and `on_list`; the undo rate per `from`; funnel `ws_message_copied` → `ws_action` `follow_up` / `record` within 1 hour, breakdown `where`.
