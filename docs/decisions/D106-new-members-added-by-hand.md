## D106 — New members added by hand: a pending member whose facts move to the roster member of the same name key, never on a fuzzy match (2026-11-17, owner, 11x; amends D80, D96)

Why: an officer testing the Officers' Desk asked for a way to record a member who joined today. The roster comes from the end-of-day read at 23:30 server time (D72), so a player who joined today is unknown until tonight. In the screenshot import, a row read as that player's name showed "not found" and Save stayed off ("Row #1 needs a member. Pick one, or drop the row."), so the value was lost. The owner: "an option to do it manually, then we can reconcile if needed".

- **Storage: `pending_members` plus moving facts by key.** A pending member is one row (`pending_members`, migration `0030_pending_members`): workspace, the name as typed, its name key, the add's request id, who added it and when, and `matched_uid` / `matched_at` once it is matched. Its facts are ordinary `member_facts` rows under the uid `-id` (game uids are positive). So there is one facts pipeline: the facts editor, `saveFacts`, its versions, its 409 and its merges serve a pending member unchanged, and the facts route accepts the negative uid. A separate facts table for pending members, or a pending flag on every fact, would have needed a second read and a second write path.
- **Adding one.**
  - Members tab: "Add a new member" opens the facts editor with a name field first ("Name in the game", required) and the same fields below. Save sends `POST /api/w/[slug]/pending {action: "add", requestId, name, changes}`.
  - The add carries the sheet's request id (D100). A repeat of the same request answers with the first add's member and stores nothing. A name with no name key (only decoration) answers `400 bad_name`. Without a session it answers `401 signed_out` (D99).
  - An open pending member with the same name key is reused instead of a second one (a partial unique index on workspace and key while unmatched).
  - It shows above the list under "New members", tagged "New · waiting for tonight's roster" (a neutral `Tag`). Its sheet has the facts (Edit, Paste what they told you), "Link to a member" and Delete. Delete asks first (`AskSheet`) and deletes the pending member with its facts and Alliance Duel points.
- **From the screenshot import.** A row "not found" offers "New member: <read name>" under the member picker. Choosing it shows the name in a field to fix (the OCR misreads names) and "Pick a member instead". On Save, inside the save's transaction, the name opens the pending member with that name key or makes one, and the row saves to it: Alliance Duel points under its uid, a member update's facts as a new version "from a message". Two rows that turn out to be the same member and fact refuse the save (`bad_rows`). Pending members are also listed at the end of every row's picker, under "New, waiting for the roster". The draft is still the only thing that makes them: discarding the draft makes none.
- **Reconciling.**
  - When: each time the Members tab is read, against the alliance's newest roster of any kind (the one the tab shows), for the pending members added at or before that roster's read time. So the end-of-day read of the evening a member was added, or any later roster read, is the first that can match them. It does not run inside the end-of-day read (`lib/daily-read.ts`): D71's fence keeps `lib/private` out of the public read.
  - Who matches: a member of that roster who has no facts yet in this workspace, whose name has the pending member's name key, or whose uid that key is remembered for (`name_aliases`).
  - Exactly one: in one transaction the pending member is claimed (`matched_uid` set where it is still null, so two officers opening the tab at once move it once), its facts move to the member (`version` + the member's newest version of that field, 0 when none, so versions and times are kept), its Alliance Duel points move too (a day the member already has keeps the member's), and the name key is remembered as an alias for that uid (confirmed by nobody: the roster matched it).
  - None or several: it stays pending. Its sheet then says "The daily update of <date> had no single match. Link them to a member, or wait for the next one."
  - Never on a fuzzy match: only an equal name key or a remembered alias moves facts.
- **Link to a member.** The officer's pick from the newest roster: the five closest names first ("Closest names", by edit distance between name keys, `closestNames` in `lib/screenshot/match-name.ts`), then everyone else by name, and a search by name key. The move is the same as above, also when the member already has facts: the pending member's versions are appended after the member's, so the append-only, one-version-per-field rule holds and the pending member's values become the newest.
- **The import's picker (C).** A doubtful row already put the matcher's suggestions first under "Closest names", then everyone by name. A row not found had no suggestions; it now gets the three closest names under the same group.
- **Privacy.** A pending member has a name, the officer's facts and the points saved for them; no roster field. Nothing is logged (`privately`).
- **Not done.** No warning when the typed name is already a current member's (the next roster read then matches that member if they have no facts, or the officer links by hand). A pending member is not in roll calls, caravan or Elixir suggestions, counts or the alliance's numbers until it is matched.
- **Amendment 2026-11-17 (11x2, owner answers): a name already in the alliance, "To match", and delete keeps the record.**
  - **Name already a member's.** In "Add a new member" and in the import's "New member" row, a name whose name key is a current member's (newest roster, `sameName` in `lib/private/roster-search.ts`) shows "<name> is already in the alliance. Open them instead?" with "Open" (the Members list searched for that name, `?q=`) and "Add anyway". Save stays off until the officer answers; "Add anyway" holds for that name key only. In the import the same line reads "Pick them instead?" with "Pick them": the row takes that member (or goes back to the picker when several members share the name), since leaving the draft would lose its fixes; the draft's Save says "Row <n>: that name is already in the alliance. Pick them, or tap Add anyway." Game names can repeat, so officers decide; the server does not refuse it.
  - **To match.** Matching on read stays as above. A pending member is "To match" once a roster read at or after its add (normally the end-of-day read about 23:37 ST) still gives no single match: open, and added at or before the newest roster's read time (`toMatch`). Computed on read, never by the nightly job (D71's fence). Home runs the same match first and shows "<n> new members to match" in its "To review" box, linking to Members (`#to-match`). Members shows them at the top of "New members" with that line, a short reason and "Link to a member" on each; their tag reads "To match" instead of "New · waiting for tonight's roster".
  - **Delete keeps the record** (replaces "deletes the pending member with its facts and Alliance Duel points"). Delete sets `pending_members.dismissed_at` (migration `0033_pending_members_dismissed`); the row, its facts and its points stay. An open pending member is one neither matched nor dismissed; the one-open-per-name-key index skips dismissed rows. They are listed read-only under "Dismissed (<n>)", a closed `details` below "Add a new member", each with the day it was dismissed and its facts on one line. Adding the same name key again (by hand or from the import) reopens the newest dismissed one, with the new name as typed and the add's time, so its facts come back; an add from the add sheet whose facts meet stored ones answers 409 as any facts save does. The import's "New member" row never conflicts: the officer saw no facts for it, so each fact is written at the pending member's current version of that field (fill or append, as D80's sheet import): an equal value is left as it is, another value appends the next version. The question reads "Delete <name> from the list? The info added here is kept under Dismissed."
- **Amendment 2026-11-17 (11x2 review, PR 388): one verb per action, plain words, "Bring back".** Replaces the words quoted in the amendment above; the behavior is unchanged except where said.
  - **Remove, not Delete.** The action is "Remove" (PT "Tirar", FR "Retirer"): "Remove {name} from the list?   - **Needs linking, not To match.** "1 new member needs linking" (PT "1 membro novo para vincular", FR "à associer"), tag "Needs linking" (PT "Falta vincular"), button PT "Vincular a um membro" ("ligar" reads as "to phone").   - **Name already a member's.** "{name} is already in the alliance. Open {name}, or add a second {name}?" with "Open {name}" (filled) and "Add anyway"; in the import "Use {name}" instead of "Open {name}". While Save is off the sheet says "Answer the question above first."
  - **Nightly roster.** One term: the add sheet says "For someone who joined today. Their notes attach to their player after the nightly roster (<DAILY_ROSTER_AT> server time)." and the tag "New · waiting for the nightly roster". The time comes from `DAILY_ROSTER_AT`, not a written number.
  - **Robustness.** Members and Home run the match through `matchOnRead`: one read of the open pending members serves the match and the list or count, and a failed match logs the code `w.pending.match_failed` only and the page shows the pending members unmatched. The time-zone picker's "used in the alliance" order counts only the newest roster's members and open new members (`usedZones`), not former or removed ones. A conflict on an import "New member" row is shown on that row (matched by name key to its pending member).
