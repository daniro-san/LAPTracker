## D150 — A committed e2e suite: Playwright on a production build, a Postgres service container in CI, invented data, nothing leaves the machine (2026-11-21, owner, issue 477; uses D47, D71, D99, D131)

Why: every build session wrote its own throwaway e2e script in a scratchpad (a local production build, the db:local cluster, an officer session written into the database, playwright-core with the system Chrome). None of it was committed, so a regression between sessions, such as the member card that opened again after closing (#573) or Raid prep's "To mark" counting a wall mark (#590 F1), was caught only when someone looked again. The owner approved a committed suite on 2026-11-21 as the main gap before agents run issues end to end.

**The dependency.** `@playwright/test` 1.65.0, exact, a dev dependency.

- **Why a package:** the platform has no browser driver, and `@playwright/test` is the standard runner for one: projects per window size, web servers it starts and stops, traces on failure. The QA sessions already drove Chrome through `playwright-core`, the same engine, from outside the repo.
- **Release date:** 2026-11-05 (16 days before it was added; 1.65.1 of 2026-11-13 was too new).
- **What it adds:** `@playwright/test`, `playwright` and `playwright-core`, all 1.65.0, with no other dependency (about 19 MB in `node_modules`).
- **Install scripts:** none in any of the three. No browser is downloaded at install: `pnpm exec playwright install chromium` does it, run by hand locally and by the e2e workflow in CI. Nothing is added to `allowBuilds` (D10).

**The harness** (`playwright.config.ts`, `e2e/`):

- **The app** is a production build: `next build`, then `next start` on 127.0.0.1:3477, reached as `http://localhost:3477`, because browsers keep a Secure `__Host-` cookie on `localhost` over plain http and `next start` names its own origin `localhost` for the same-origin check on writes. `E2E_NO_BUILD=1` reuses the last build. The public pages' shared reads (D143) are kept in `.next/cache/fetch-cache` between server starts, so the command empties that folder before `next start`; the server is never reused from an earlier run.
- **The database** is a local Postgres reached through the db:local bridge (D47) on port 54377. `e2e/global-setup.ts` drops and recreates the database named in `E2E_DATABASE_URL` (default `postgres://lap:lap@127.0.0.1:54320/lap_e2e`, the db:local cluster's port), refuses unless the host is `localhost` or `127.0.0.1` and the name contains `e2e`, applies `drizzle/` with `scripts/db-local.mjs migrate`, and loads the seed with `psql`.
- **The seed** (`e2e/fixtures/seed.ts`, invented names only) is built from the day the suite runs, in server time, so every run sees the same week: two alliances with a workspace each (Lantern Keep `lnk`, Moss Hollow `msh`) and three without, 14 daily rosters, the ranks board and tracked set of yesterday, two past Saturday events (in the last one, one Lantern Keep member left and one joined), Raid prep on the next Saturday on or after today (the Me page lists only roll calls from today on) with 4 Shield marks and 2 wall-only marks, this week's cheese entry with no roll call yet, and an officer's and a member's session per workspace (member links approved). Sessions are rows in `workspace_sessions` with the sha256 of a fixed invented token, sent as the `__Host-lap_ws.<slug>` cookie (D131); no Discord call is made or stubbed. The global setup puts the moment it seeded at in `E2E_NOW`, and the specs lay out their dates from it.
- **Sentinels.** Each alliance's raw_json members carry their own values for `x`, `y`, `last_online_at` and `joined_at` (six-digit coordinates; four years from 2086 to 2092 that no page shows otherwise; last online on a 29 February, which the member card prints as "Feb 29" without the year), and every `avatar_url` is on `e2e-avatar-sentinel.invalid`, so a leak can be told from any page or answer, and whose it is.

**Nothing leaves the machine.** The server's settings (`e2e/env.ts`) set every key of `.env.example`, empty when unused, because Next does not let `.env.local` override a variable that is already set: a developer's own keys never reach the e2e server. The upstream API, Discord's API and PostHog's API point at `127.0.0.1:9`; Groq, webhooks, the tracker keys, push and analytics are unset. Two guards fail the run on any other host:

- in the browser, every request to a host other than `localhost` or `127.0.0.1` is aborted and fails its test (`e2e/fixtures/test.ts`);
- in the server, `e2e/no-network.mjs` (loaded with `--import` into `next start`) refuses every name lookup but `localhost`, writes the host to `test-results/e2e-outbound.log`, and the global teardown fails the run if that file is not empty. `fetch`, `http`, `https`, `net` and WebSocket all look names up through `node:dns`; an address such as `127.0.0.1:9` needs no lookup.

**The privacy check** (CLAUDE.md "Roster fields", D71). Every HTML, JSON and RSC answer a test's pages receive, and every page and API of a sweep per viewer, is searched for the sentinels: the coordinates as sent or with a thousands separator, the years, "Feb 29" in EN, PT and FR, and the photo host. Public pages and the members' board show none. A workspace's desk shows only its own alliance's: `joined_at` on its pages (the Members "Copy for spreadsheet" row carries it; D71 keeps x, y, online and last_online_at out of copies), and the map position and last online only in an officer's member card (`/api/w/<slug>/members/<uid>`), which the sweep also checks does carry its own coordinate and "Feb 29", so the check is known to see them. `online` is a boolean with no sentinel value: it is caught only as a JSON key. No answer carries the photo URL. JSON answers are also checked for the keys `x`, `y`, `online`, `last_online_at`, `joined_at` and `avatar_url`, and `lastOnlineAt`, `joinedAt` and `avatarUrl`. A private answer of one workspace never names the other workspace's members.

**The flows**, each at 390 px (project `phone`, touch on) and 1280 px (`wide`); the isolation spec on `phone` only:

- public: the home ledger, the alliance list, a player page, an event's ledger with the member-change mark and its split;
- the desk: Home; Members, a card opened from the list and closed, still closed 1.5 s later with no "Loading…" and no `?m=` (#573); Roll call, a mark that is kept after a reload; Raid prep, "To mark 7" and "4 of 11 marked" (#590 F1);
- the board: a member's Me page with their own data only, and a member's session sent from the desk to the board;
- isolation: each workspace's officer and member, with their token in their own cookie, in the other workspace's cookie name, or in the cookie of before D131, gets `401 signed_out` from the other workspace's member card, activity, read status and roll call write, and, with each of the three cookies, only the sign-in screen on its desk and board pages; a member's session gets `401` from its own workspace's desk APIs; an officer asking for the other alliance's member through their own workspace gets `404` (card) and `400 not_member` (mark).

**CI** (`.github/workflows/e2e.yml`): a workflow of its own, so the `check` job the rulesets require stays as it is. It runs on `pull_request` when a PR changes what the app runs (`app/`, `lib/`, `config/`, `drizzle/`, `e2e/`, `public/`, the db:local scripts, the root config files, `package.json`, the lockfile, `pnpm-workspace.yaml`, `.nvmrc`) and by hand; a docs-only PR starts no job. Postgres 18.6 is a service container (pinned by digest) with password auth, as the db:local cluster has. The pnpm store and the Playwright browser (headless shell only) are cached; the browser's system libraries come from apt each run. `next build` is its own step (its time shows apart and does not count against the web server's 300 s timeout), then `E2E_NO_BUILD=1 pnpm test:e2e`. The build downloads the Google Fonts that `next/font` self-hosts (`lib/brand/fonts.ts`); that is build time, outside the guards, and the only outside call of the job besides the action, package, image and browser downloads. A failure uploads `playwright-report/` and `test-results/` (traces, screenshots, the outbound log) for 7 days; they hold invented data only. The job is not a required check.

**Not done here:** a nightly run on `dev` (the issue's proposal) waits for the Actions minutes measure (2026-11-19); WebKit, the issue's sign-in, calendar, notices, feature-switch, tracker key and export flows (D71's export rule is not swept), and the other 34 `/api/w/[slug]` routes in the cross-workspace check, are follow-ups.
