## D150 — A committed e2e suite: Playwright on a production build, a Postgres service container in CI, invented data, the app under test reaches nothing outside the machine; a required check, and WebKit on every release (2026-11-21, owner, issue 477; uses D47, D71, D99, D131)

Why: every build session wrote its own throwaway e2e script in a scratchpad (a local production build, the db:local cluster, an officer session written into the database, playwright-core with the system Chrome). None of it was committed, so a regression between sessions, such as the member card that opened again after closing (#573) or Raid prep's "To mark" counting a wall mark (#590 F1), was caught only when someone looked again. The owner approved a committed suite on 2026-11-21 as the main gap before agents run issues end to end.

**The dependency.** `@playwright/test` 1.65.0, exact, a dev dependency.

- **Why a package:** the platform has no browser driver, and `@playwright/test` is the standard runner for one: projects per window size, web servers it starts and stops, traces on failure. The QA sessions already drove Chrome through `playwright-core`, the same engine, from outside the repo.
- **Release date:** 2026-11-05 (16 days before it was added; 1.65.1 of 2026-11-13 was too new).
- **What it adds:** `@playwright/test`, `playwright` and `playwright-core`, all 1.65.0, with no other dependency (about 19 MB in `node_modules`).
- **Install scripts:** none in any of the three. No browser is downloaded at install: `pnpm exec playwright install chromium` (and `webkit`) does it, run by hand locally and by the e2e workflow in CI. Nothing is added to `allowBuilds` (D10).

**The harness** (`playwright.config.ts`, `e2e/`):

- **The app** is a production build: `next build`, then `next start` on 127.0.0.1:3477, reached as `http://localhost:3477`, because browsers keep a Secure `__Host-` cookie on `localhost` over plain http and `next start` names its own origin `localhost` for the same-origin check on writes. `E2E_NO_BUILD=1` (exactly `1`) reuses the last build. The public pages' shared reads (D143) are kept in `.next/cache/fetch-cache` between server starts, so the command empties that folder before `next start`; the server is never reused from an earlier run.
- **The database** is a local Postgres reached through the db:local bridge (D47) on port 54377. `e2e/global-setup.ts` checks the URL in `E2E_DATABASE_URL` (default `postgres://lap:lap@127.0.0.1:54320/lap_e2e`, the db:local cluster's port) before anything else: the database name must contain `e2e`, and `scripts/db-local.mjs check` must pass (the host is `localhost` or `127.0.0.1` for every reader of the URL, with no `host`, `hostaddr` or `service` parameter, and the bridge listens). Only then does it drop and recreate the database, apply `drizzle/` with `scripts/db-local.mjs migrate`, and load the seed with `psql`.
- **The seed** (`e2e/fixtures/seed.ts`, invented names only) is built from the day the suite runs, in server time, so every run sees the same week: two alliances with a workspace each (Lantern Keep `lnk`, Moss Hollow `msh`) and three without, 14 daily rosters, the ranks board and tracked set of yesterday, two past Saturday events (in the last one, one Lantern Keep member left and one joined), Raid prep on the next Saturday on or after today (the Me page lists only roll calls from today on) with 4 Shield marks and 2 wall-only marks, this week's cheese entry with no roll call yet, and an officer's and a member's session per workspace (member links approved). Sessions are rows in `workspace_sessions` with the sha256 of a fixed invented token, sent as the `__Host-lap_ws.<slug>` cookie (D131); no Discord call is made or stubbed. The global setup puts the moment it seeded at in `E2E_NOW`, and the specs lay out their dates from it. The seed is SQL text, not `lib/schema` inserts: a renamed column fails the e2e check, which is required (below).
- **Sentinels.** Each alliance's raw_json members carry their own values for `x`, `y`, `last_online_at` and `joined_at` (six-digit coordinates; four years from 2086 to 2092 that no page shows otherwise; last online on a 29 February, which the member card prints as "Feb 29" without the year), and every `avatar_url` is on `e2e-avatar-sentinel.invalid`, so a leak can be told from any page or answer, and whose it is. `online` stays a boolean, as the upstream sends it, so it has no sentinel value; its key is checked instead.

**The app under test reaches nothing outside the machine.** The server's settings (`e2e/env.ts`) set every key of `.env.example` the app reads, empty when unused, because Next does not let `.env.local` override a variable that is already set: a developer's own keys never reach the e2e server. The upstream API, Discord's API and PostHog's API point at `127.0.0.1:9`; Groq, webhooks, the tracker keys, push and analytics are unset. Two guards fail the run on any other host:

- in the browser, every request to a host other than `localhost` or `127.0.0.1` is aborted and fails its test (`e2e/fixtures/test.ts`);
- in the server, `e2e/no-network.mjs` (loaded with `--import` into `next start`) refuses every name lookup but `localhost`, and every socket to an IP address that is not loopback (`net.Socket.prototype.connect`, which `net`, `tls`, `http`, `https`, `fetch` and WebSocket all go through). It writes each refused host to `e2e-outbound.log` at the repository root, outside `test-results/` (which Playwright empties after the config loads); the config deletes the file before the servers start, the guard makes it on its first refusal, and the global teardown fails the run if it holds any host. A refusal while the servers start is kept.
- **Not guarded:** `next build`. It downloads the Google Fonts that `next/font` self-hosts (`lib/brand/fonts.ts`). That, and the action, package, image and browser downloads, are the only outside calls of the job.

**The privacy check** (CLAUDE.md "Roster fields", D71), on every HTML, JSON and RSC answer a test's pages receive, and on every page and API of a sweep per viewer:

- the sentinels: the coordinates as sent or with a thousands separator, after a comma too (`[x,y]` pairs, CSV columns) or a JSON escape such as `\t`; the years; "Feb 29" in EN, PT and FR; the photo host;
- the fields' names as keys, in JSON and in the escaped RSC payload inside the HTML: `online`, `last_online_at`/`lastOnlineAt`, `joined_at`/`joinedAt`, `avatar_url`/`avatarUrl` (`x` and `y` are left to their sentinels: SVG props use those keys);
- a private answer of one workspace never names the other workspace's members;
- an answer that cannot be read fails the test; only a redirect is skipped.

Public pages and the members' board show none. A workspace's desk shows only its own alliance's: `joined_at` on its pages (the Members "Copy for spreadsheet" row carries it; D71 keeps x, y, online and last_online_at out of copies), and the map position, online and last online only in an officer's member card (`/api/w/<slug>/members/<uid>`). Positive controls: the officer's own card is scanned as if a public page had sent it and must show `a.x`, `a.y` and "Feb 29"; the Members page the same way must show `a.joined_at`. So the passes are not blind.

**What a test checks: the screen** (owner, 2026-11-21). A test asserts what the user sees, never a status code or a request alone (API checks are extra guards):

- the page heading, the key values of the flow in their row, card or region (`getByRole` and the region's name), and no error screen (the error boundary's, not-found's and database-down titles from `lib/copy-errors.ts`) or empty state where the seed put data;
- the values are computed from the seed's own rows (`eventTotals`, `memberChange`, `endOf`, `rosterOf`, `boardOf`, `weekLine`, `DAILY` in `e2e/fixtures/seed.ts`) and written with the pages' formatter (`compactLarge`, D78), in their rendered text (`innerText`: the exact figures the page hides for "Exact numbers" do not count); dates follow the run day and are written as the page writes them;
- after an action (a tap, a save, a close), the screen changes as a user sees it, and the change is still there after a reload, or on the page the flow names (the roll call list), and is then put back, with that checked on screen too;
- no pixel snapshots; no fixed waits: `page.clock` moves time for "a moment after closing", and a tap waits for React to have hydrated its button (the element carries React's props key; not `networkidle`, which the read status bar's polling defeats);
- a test that writes uses rows no other test reads: one cheese roll call per project and repeat (`cheeseOf`, nine weekly entries), and Raid prep's mark on a later week of its own per repeat (`raidOf`), on the phone project only. The desk Home's activity feed changes with those writes, so Home checks only that its newest line is the officer's.
- the global setup refuses to start within 10 minutes of 02:00 UTC, when the server's day (UTC−2) changes.

**The flows** (28 tests), each at 360 px (project `phone`, touch on) and 1280 px (`wide`); the isolation spec on `phone` only; with `E2E_WEBKIT=1` the desk flows also on WebKit (project `iphone`, the iPhone 15 profile at 360 px):

- public: the last event's ledger on `/` and `/events/2` (each workspace's rank, End might and kills, their ▼/▲ changes with percentages, members joined and left), the alliance list (yesterday's ranks board: rank, might, kills), a player page (might, kills, level at the last event's End), the member-change mark and its four split lines (total, joined, left, without them), each with no sideways scroll;
- the desk: Home (the alliance's header, the D146 week line with this or last week's donations, the top donors); Members (the count, a member's line with rank and might, the joiner's "first seen", no leaver; the card's might and kills, the 7-day averages, yesterday's bar and the might change; the map position hidden until "Show map position"; closed, still closed after 1.5 s of page time and after a reload, #573); Roll call (the list's counts, a mark shown at once, kept after a reload and in the list, then cleared the same way); Raid prep ("To mark 7", "4 of 11 marked", the wall-only members still to mark, #590 F1; and on phone a Shield mark that moves "To mark" and survives a reload, then clears);
- the board: the Me page (the Raid prep mark, the linked name, own might and kills with their change since the first roster, this and last week's averages, no other member's name, `Cache-Control: private, no-store`), and a member's session sent from the desk to the board (its heading and the next 7 days from today);
- isolation: each workspace's officer and member, with their token in their own cookie, in the other workspace's cookie name, or in the cookie of before D131, gets `401 signed_out` from the other workspace's member card, activity, read status and roll call write; with each of the three cookies the other workspace's desk and board pages show the sign-in screen (its heading, words and button) and none of that alliance's tag, name, members or mights; a member's session gets `401` from its own workspace's desk APIs; an officer asking for the other alliance's member through their own workspace gets `404` (card) and `400 not_member` (mark), and their own Raid prep still shows its roster and none of the other alliance's members. Each sweep first checks it got the real page (not the sign-in screen's heading; the alliance, player or signed-in person's name in it) and `Cache-Control: private, no-store` on every `/w` and `/api/w` answer, then scans it.

**CI** (`.github/workflows/e2e.yml`), a workflow of its own; `ci.yml` and its `check` job stay as they are.

- **A required check** (owner, 2026-11-21, after a persona panel): it runs on every `pull_request` into `dev` (`branches: [dev]`; release PRs into `main` do not run it again, the release dispatch below covers them), with no workflow `paths` filter, so every PR gets a job named `e2e`. Its first step diffs the PR against its base (`git diff --no-renames`, so a rename out of an app path still counts as a change to it) over the paths the app runs on (`app/`, `lib/`, `config/`, `drizzle/`, `e2e/`, `public/`, the db:local scripts, the root config files, `package.json`, the lockfile, `pnpm-workspace.yaml`, `.nvmrc`, the workflow itself); with none changed it skips the install, build and tests and passes. The owner adds the check to the `dev` ruleset.
- **Flakes:** `retries: 0`, in CI too; no retry hides a flake. If a random failure blocks a PR, the required check is removed until the flake is fixed.
- **On what ships:** `release-prepare.yml` dispatches it on `dev` right after `ci` (`gh workflow run e2e.yml --ref dev`; the workflow already has `actions: write`). A daily cron at 03:17 UTC also runs it, as a bonus: GitHub fired `tick`'s schedule in about 4% of its slots, so the cron alone is not relied on. GitHub runs a schedule from the default branch (`main`), so the job checks out `dev`; the cron starts only once a release has copied the workflow to `main`.
- **WebKit on every run that is not a pull request** (the release dispatch, the cron, a run by hand): `E2E_WEBKIT=1` and `playwright install --with-deps webkit`. Basis: PostHog, 30 days: about 11% of desk views are iOS/WebKit, almost all from one device; about 86% are Chromium. Condition: if a WebKit-only bug reaches production, WebKit moves to every PR.
- **The job:** Postgres 18.6 is a service container (pinned by digest) with password auth, as the db:local cluster has. The repository's Actions cache is shared and near its 10 GB limit (9.7 GB, 2026-11-21), so a pull request only restores (`actions/cache/restore`, by prefix) the Playwright browsers and `.next/cache`; the runs on `dev` save them (`actions/cache/save`, keyed with the run id), with both browsers installed, so every PR finds both. The pnpm store is setup-node's cache. The browsers' system libraries come from apt each run. `next build` is its own step (its time shows apart and does not count against the web server's 300 s timeout); `.next/cache` is saved right after it, before the tests fill its fetch cache; then `E2E_NO_BUILD=1 pnpm test:e2e`. A failure uploads `playwright-report/`, `test-results/` and `e2e-outbound.log` for 7 days; they hold invented data only. `concurrency` cancels a run when a newer one starts on the same ref.
- **Measured:** the first run on PR #600 took 132 s in all: `next build` 51 s, the tests 37 s.

**Not done here** (follow-ups): sign-in and sign-out (with its own session), Follow-up, Calendar add/delete/Undo, notices (save, translate, publish), member facts, a feature switch (its own workspace or phone only), the export ZIP sweep (D71's export rule), compare, the live event page, viewer settings, the other 34 `/api/w/[slug]` routes in the cross-workspace check, a realistic roster (about 95 invented members), and unit tests for `proxy.ts`.
