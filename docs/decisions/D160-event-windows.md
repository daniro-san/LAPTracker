## D160 — Event windows: an event has 1 to 4 windows, each with its own Before, After and samples; its change is the sum of its windows' changes (2026-11-27, owner 2026-11-16, issue #290, build 1b of #183; amends D1, D21, D31, D69 and budget.reserve-for-after)

Why: Origin of Chaos is one game event with two windows, 00:10–00:40 and 12:30–13:00 server (owner, 2026-11-07 and 2026-11-08). The next one is Saturday 2026-12-05. Spike #183 chose Option B: the event owns its windows, each window owns its readings. D69 (build 1a) added samples to one-window events only.

- **Shape.** Table `event_windows (event_id, n, before_at, after_at)`, primary key `(event_id, n)`, `n` 1 to 4, cascade on the event's delete (a pruned rehearsal). `events.before_at` stays window 1's Before and `events.after_at` the last window's After. `snapshots.window_n` (default 1) names the row's window; `snapshots.between_windows` is true on a Before or After that lies between two windows (window 1's After, window 2's Before, and so on). One Before and one After per window: the partial unique index `snapshots_event_window_phase_unique (event_id, window_n, phase) where phase <> 'sample'` replaces `snapshots_event_phase_unique`. Samples keep `snapshots_event_slot_unique (event_id, slot_at)`: windows never overlap, so a slot is in one window. Migration 0080 makes every existing event a one-window event (window 1 from its own times; every existing row is window 1 and not between windows). No foreign key from `snapshots` to `event_windows`: rows inserted by hand (tests, the seed) are one-window events with no window row, and `getEventWindows` reads them as one window.
- **Readers keep one predicate.** `phaseSnapshot` now means the event's Start (window 1's Before) and End (the last window's After): `phase <> 'sample' and not between_windows`. Every reader that showed a Start or an End shows the same rows as before, also for a two-window event. The rows between windows are read only through `betweenWindows` / `betweenWindowIds`, to sum the windows' changes. Readers that join `member_snapshots` and group by phase (player pages, the workspace's event might, a member's own Start) now filter with `phaseSnapshot` too, because the rows between windows are full reads with member rows.
- **The change.** An event's change is the sum of its windows' changes, each window's After − Before, and null when any window's change is null (INVARIANT `freshness.no-stale-delta`). It is computed by `windowedStart(start, between)` (`lib/compute.ts`): the Start shifted by what changed between the windows, so `delta(windowedStart(...), end)` equals the sum. The shifted Start is used for changes only, never shown. Readers moved: the event page's ledger rows and alliance movers (`comparisonRows`, `allianceMovers`), member movers, who gained kills (`memberTurnout`), kill share vs might share (each window's Before paired with its own After), compare (D57) alliance and member views, the player compare, the alliance page's chain (`allianceHistory` in-event change) and the End's Discord message and picture. A one-window event has no rows between windows, so every one of these returns what it returned before.
- **Across events.** The reference reading of an event stays "the End, else the Start": the End is the last window's After. Ranks are read at the Start and the End.
- **Member history (D60)** lists the event's Start and End rosters; its changes are from one roster to the next, so the rows between windows are not cards.
- **Tick.** `duePhases` and `dueSample` read `event_windows`: each window's Before and After has its own due window (`SNAPSHOT_WINDOW_MIN`), and samples run strictly between a window's Before slot and its After, once its Before has finished and while it has no After. Between windows nothing is due. `findOrCreateEvent` stores the windows with the event in one transaction; an event that has no window row (made by the build before D160 between a release's migration and its deployment) gets window 1 from its own times. The schedule from the env (D1) is still one window (`ScheduledEvent.windows`); the D141 clock gate opens per window (`tickClockDue`), so a two-window schedule wakes the database only inside its windows.
- **Collector.** A later window's Before reads the event's stored alliance list, like an After (INVARIANT `event.after-uses-event-copy`): every window reads the same alliances. Each window's Before and After is a full read (member rows, `raw_json`, ranks board, D5's fallback).
- **Budget** (INVARIANT `budget.reserve-for-later-windows`). `requiredQuota(n, laterReads)` and `sampleQuota(n, k, laterReads)` add one read's reserve (n + 5) for each Before and After of the event's other windows still due on the same UTC day (`laterWindowReads`). For Origin of Chaos (both windows on one UTC day, 02:00–15:15 UTC): window 1's Before and After and its samples need 100 and 181 calls for 20 alliances, window 2's 50 and 131. `dailyReadQuota` reserves the event windows' reads still due on its quota day (`eventReadsDueToday`); the 23:30 server read of Friday is 01:30 UTC Saturday, the quota day of both windows, so it keeps 100 for the event. The squads reserve counts every window's reads and samples. Origin of Chaos costs 4 full reads and 5 samples: about 189–207 calls.
- **Discord (amends D31; owner answers 11 and 16).** The public message is posted by window 1's Before and edited once, by the last window's After; a Before or After between windows posts nothing public. The End's text and picture show the event's change (the sum of the windows). The admin message is posted by window 1's Before and edited at each window's After; a later window's Before does not edit it, and posts its own message only when it ends partial or failed. A sample that falls short posts at most one admin message per window (INVARIANT `notify.sample-once-per-event`, now per window).
- **Not in this decision.** Schedules from /admin, the 4-week cycle and one-off alliance events (#175, build 2): until they exist, the env's weekly event is the only scheduled event and it has one window. The live views (D69's pulse, the fight clock, the standings "so far", D86) read the Start, the samples and the End; between windows they show the gap as missing slots and their "so far" figures include what changed between the windows.
- **Release.** Apply migration 0080 at a time with no Before, After or manual round due: the previous build's claim (`on conflict (event_id, phase)`) has no matching index once 0080 is applied. Never roll back below 0080.
