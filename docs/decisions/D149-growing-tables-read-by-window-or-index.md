## D149 — Reads of tables that grow forever take a window or an index: the desk's facts and /admin's first roll call (2026-11-21, perf panel, issue 521 follow-up; amends D109, D144, D145)

Why: the owner (2026-11-21) asked that nothing fetch "tons of data at once". An audit listed every table and how it is pruned, and every read of a growing table with no window, no LIMIT or no supporting index. It measured each one through the real lib functions on invented data at one year of scale: 10 workspaces, 30 alliances read daily, 222k member facts, 299k roll call marks, 20k notice posts and 366k player reads, on Postgres 18. The handoff `docs/handoff/perf-unbounded-reads.md` has the inventory and the numbers. Three reads grew with the whole history and ran on every view. Each now returns the same rows as before and reads them through an index.

**The newest member facts** (`latestFacts`, `lib/repo/member-facts.ts`). It feeds `factsOf`: Home, Members, every member card, Follow-up, the roll call pages, Raid prep, caravans, Insights, the imports, and the tick's Raid prep fill. It was `DISTINCT ON` over every version, and the squads read adds a "Main squad might" version whenever the value differs. It is now a recursive read that walks `member_facts_version_unique` backwards. Each (member, field) pair costs one index descent, which lands on that pair's newest version. So it grows with the pairs (about 7 a member), not with the versions. It returns the same rows in the same order (by member, then field). Each value goes through the jsonb column's own decoder, as Drizzle's selects do, so a value reads the same as through `factHistory` and `factVersion`. Measured: 11.2 ms to 5.0 ms per call. Buffer hits stay about the same today (3.0k to 2.8k), so the gain now is the sort's CPU. The cost stays flat as versions pile up: after a wake it touches about 120 table pages per workspace instead of about 3,000.

**The thanks' progress** (`progressHistory`, `lib/private/members.ts`, on `factHistorySince`; amends D109). Home and Members read every main squad and AD Tech version of the workspace. `progressOf` uses only two versions per pair: the last saved before the thanks week's Monday 00:00 ST, and the last saved in that week. The read now takes:

- the versions saved from one day before that Monday (00:00 UTC) on, through `member_facts_workspace_written_idx`;
- for each pair that has one of those versions, the newest version saved before.

A pair with no version in the week gives no progress, as before. The day of room covers any server zone's offset, and `progressOf` still splits the week by server day itself. So the thanks are the same as when it read the whole history. The card's trend keeps reading its own member's whole history (`factHistory` with a uid), which stays bounded per member. Measured: 15.4 ms to 0.8 ms. An old-against-new check matched on every row: 45,746 progress rows over 4 zones, every 3 hours across two weeks, Mondays included.

**/admin's "First roll call marked"** (`allianceUsage`, `lib/queries/admin-alliances.ts`; amends D144's cost and D145). This part read the whole `roll_call_marks` table on every /admin render. That is up to about 120 an hour in the minutes after each tick, and every 4 s while a run goes. A new index, `roll_call_marks_call_written_idx (roll_call_id, written_at)` (migration `0066_roll_call_marks_call_written`), gives each roll call's first mark from the index alone. The part takes the earliest of those per workspace. It still counts deleted and archived roll calls (D145) and still returns null for a workspace with none marked. Marks and roll calls are never hard-deleted (D123); only a workspace purge removes them. So the first mark never moves. The part still grows with the roll calls (about 260 a workspace a year), as before, since a roll call holds about the same number of marks. What changes is that it reads one index entry per roll call instead of about 115 marks. Measured: the statement went from 19.3 ms to 6.2 ms. Buffer hits went up, from 2.8k to 7.8k: about 3 per probe, all index pages. After a wake, Neon reads about 1,100 random index pages instead of 2,800 table pages read in order. The index is 9.2 MB at 300k marks and costs one more index entry per mark written.

The part depends on this index. Without it, the planner walks `roll_call_marks_written_idx` for each roll call: 12.8 s and 4M buffers per /admin render on the same data, and a `min()` form does the same. Deploys run `db:migrate` before the build, so the index exists before the code runs. Dropping or renaming it later needs this part changed in the same release.

**Not changed, with the measurement** (one year of invented data):

- `notice_publishes`, `garrison_plans`, `thanks_shares` and `shield_checks` on /admin (D144): 0.8 ms together at 20k notice posts, which is decades of real posting.
- `app_errors` counted by `workspace_slug`: the table holds at most 500 rows.
- The member history index reading member lists (issue 473): 1 ms, at most 15 rosters, and page 1 is shared (D143).
- `firstSeenDays` (the earliest day of every uid in the alliance's rosters): 3.4 ms on every `membersView`. It grows with the roster days, about 10 ms at three years. Its map also feeds Insights' joins and tenure, so a bounded form needs its own design. It is the next one to fix.
- `clearOldPlayerRaw` (once a day): about 9 ms warm, about 1–2 s on a fresh wake. It walks every player read older than 90 days through `player_reads_read_at_idx`: 3.9k cold pages, growing about 11 a day. A partial index `(read_at) where raw_json is not null` would bound it. A date floor would not do: a tick outage longer than the floor would leave raw bodies past 90 days (D132).
- `endOfDayReads`: limited to n rows, 8.5–16.5 ms on every Members view and card. That is now the largest cost per view, but its cost is the jsonb work on `raw_json`, not growth.
- The thefts log reads all of a workspace's thefts: that is the page's content (D97).
- `player_reads` and `player_history`: every read goes by `(union_id, uid, …)`, one member at a time.

No cache was added, and nothing on a page changed.

**Amendment 2026-11-22 (perf panel, issue 507): the 90-day clean-up gets its own partial index.** `clearOldPlayerRaw` now reads `player_reads_raw_read_at_idx (read_at) where raw_json is not null` (migration `0068_player_reads_raw_read_at`). The index holds only the reads that still keep a body, about 90 days, so the clean-up reads the day it clears instead of the whole history. On PGlite at one year (366k reads, 91k with a body), the clean-up's scan went from 5,829 table pages (a sequential scan) to 48 index and table pages, for the same 999 rows cleared. The index is 3.7 MB, against 14.8 MB for `player_reads_read_at_idx`, which stays for the windows (`shieldReadings`, `shieldPassCounts`). No date floor was added, for the reason above. The migration builds the index with a plain `CREATE INDEX`: `scripts/migrate.ts` runs each migration in one transaction, where `CONCURRENTLY` is not allowed, and the table is small: it grows about 320 KB a day for 100 members and holds about 29 MB in steady state (D132), so the build blocks the squads read's writes for well under a second, and reads not at all.
