## D126 — The owner turns features on or off per workspace on /admin, with a daily cap on each paid allowance (AI, Discord translate) and a global pause (2026-11-19, owner, 11aw, issue 450; amends D101, D113, D114, D117, D119, D124)

Why: the desk opens to other alliances (issue 438). Some features spend the owner's own limits: the Groq free tier (D81) and the Discord bot (D101). The owner (issue 450, 2026-11-19) wants to turn app features on or off per workspace on /admin, and to cap the paid ones per day. D91's PostHog flags stay as they are: they switch public-site features for every visitor, while these switches are per workspace and stored in the database.

- **"Draft the weekly thanks" is added to the AI group.** The issue's list did not name it, but it calls Groq three times (D114), so it is switched and counted like the others.
- **"Read from a screenshot" is in the AI group, as the issue lists it, but it is free.** The reader is Tesseract on our own server (D74), not Groq. So it spends no allowance, is not paid, and is on for a new workspace. Its button stays on the page; with the switch off, a press reads "Reading screenshots is turned off for your alliance." (Hiding it needs a flag passed through three word lists; left for later.)
- **"Download our data" is not a switch yet.** It is D125 (PR #449), not on `dev` when this was built. When both are merged, `export` joins the Data group with one `featureOn` line in its route and form.

**Nothing is deleted.** A switch hides and refuses; every row stays. Turning a feature on again shows everything as it was. A stored notice picture is kept while pictures are off (the weekly cleanup of D119 still runs on its own rule). A squads read that was skipped is not made up later.

**What a turned-off page says.** At its own address, inside the desk frame: the page's name, "This feature is turned off for your alliance.", "Nothing was deleted: when it is turned on again, everything is back as it was. Ask the site's owner if your alliance needs it." and "Back to Home" (EN, PT-BR, FR; `lib/private/dictionary.features.ts`). The members' board says "The members' board is turned off for your alliance." with the same second line. A refused API route answers `403 turned_off`.

**The daily caps.**

- Two allowances, each a whole number a UTC day or no cap: `ai` (Groq texts asked: one per language for Translate, one for Improve or Shorten, three for the weekly thanks) and `translate` (Discord languages: one for "for me" and each language button, one per chosen language at Post).
- **Counted atomically before the model is asked.** `useAllowance` runs one statement: `insert … select … where units <= cap on conflict (workspace, allowance, day) do update set used = used + units where used + units <= cap returning used`. Postgres locks the row for the update and checks the cap on its newest count, so two requests at the boundary never pass it. No row returned: nothing is counted, and the caller asks nothing.
- The count is for that UTC day (`workspace_usage`, keyed by workspace, allowance and day) and starts at 0 at 00:00 UTC.
- At the cap, the officer reads "This alliance's daily limit for writing help is used up. It resets at 00:00 UTC." and the Discord asker "This alliance's daily limit for translations is used up. It resets at 00:00 UTC." (`429 cap_reached` on the routes).
- D101's per-person and app-wide translation limits stay and are checked first; the workspace's count is the last check, so a refusal by any of them counts nothing.
- A request that was counted and then failed at Groq is not given back.

**The global pause.** On /admin, above the workspaces, "Paid features, every workspace": AI and Discord Translate, each Running or Paused. A pause turns every feature that spends that allowance off in every workspace, OGs included, whatever each workspace's own switches say (`allowance_pauses`, a row per paused allowance). Resume puts each workspace's own switches back.

**Defaults.**

- **OGs (`OWN_ALLIANCE_ID`): everything on, no caps.** This is today's behaviour. It comes from code, not from a data row: a workspace without a `workspace_features` row has its defaults, so the migration adds tables only and needs no data step. OGs keeps working whatever order migrations run in.
- **A new workspace: the free features on; AI and Discord translate off** (the six features in `SPENDS`), no caps, until the owner turns them on.
- **An existing workspace other than OGs** gets the same defaults as a new one: its AI and Discord Translate are off after this release until the owner turns them on on /admin.
- A row is written the first time the owner changes a switch or a cap, holding the complete settings from then on.

**/admin** (PIN only, the PIN's rate limits, `POST /api/admin/workspaces/features`).

- Each workspace's card has a "Features: n of 17 on" disclosure with today's AI and translation counts. Inside: the switches by group, each one tap ("Roll call: On"), a paid switch marked when its allowance is paused for everyone; the two caps with "Today: 12 of 50" or "Today: 12 · no cap" and Save cap; "Copy settings from" another workspace, asked first ("Replace every switch and cap of /w/a with those of /w/b?").
- Copy takes the source's settings as served, its defaults when it has no row, so copying from OGs turns everything on.
- English only (D48).

**Where it is enforced.** One rule, through `featureOn(access, key)` and `useAllowance(db, access, allowance, units, now)` (`lib/private/features.ts`):

- `requireWorkspace` and `requireBoard` read the workspace's served features with the session (one more query, in parallel), so `WorkspaceAccess` and `BoardAccess` carry them and every check after is free.
- Pages: the shared openers (`openRollCall`, `openCalendar`, `noticePage`) skip the page's reads and return the turned-off page; thefts, Start here and the board check directly. The navigation (`DeskNav`, `CalendarNav`, the Calendar week's links) leaves out what is off.
- API routes: each tab's routes, the notice and thanks drafts, the picture routes, `shots/read` and `/img/notice/[id]`.
- Discord: the interactions route finds the workspace by the server and reads its features (`featuresById`); every press of a Translate picker or language button checks them again.
- The squads read (`squadTargets` in `lib/workspace-keys.ts`) uses the catalog's rule directly: `lib/` cannot import `lib/private` (D71's fence).

**Logs and analytics.** Logs carry codes and numbers only: `features.cap_reached.ai|translate` with the workspace id and the cap, `discord.translate.turned_off`, `w.import.discord_off`. Usage counts are stored as numbers per workspace and day, nothing about who asked or what. Each owner change on /admin sends `ws_action` with feature `features` and action `turn_on`, `turn_off`, `cap`, `copy`, `pause` or `resume`, with no person (the server's fixed id) and `area` admin (`docs/analytics/tracking-plan.md`).

**For a new alliance, the owner:** registers the workspace (D71), then opens its card's Features and turns on what the alliance should have: AI and Discord Translate are off until then. Optionally set the two caps, or copy the settings of a workspace already set up.

**Tests** (one per behaviour): a turned-off tab is left out of the navigation and its route answers 403 (`lib/private/features.test.ts`, `app/(private)/api/w/[slug]/thefts/route.test.ts`); a turned-off Discord command answers the line and counts nothing, and past the cap the asker reads so (`lib/private/discord-translate-me.test.ts`); a cap stops at N and starts again the next UTC day, and two requests at the boundary let at most N through (`lib/private/features.test.ts`); OGs' defaults are everything on with no cap and a new workspace's leave the paid ones off; the /admin route refuses without the PIN; copy takes the source's settings (`app/api/admin/workspaces/features/route.test.ts`).
