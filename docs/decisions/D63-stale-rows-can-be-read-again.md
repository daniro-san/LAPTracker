## D63 — Stale rows can be read again, on request (2026-11-14, owner, 08zzzn)

Why: on 2026-11-14 the Before snapshot came back partial with all 20 alliances stale and none failed. Pressing Before again read nothing: a re-run without force reads only failed and missing alliances (D62), and "Take it again?" (force) is offered only on a complete snapshot. /admin had no way to read the stale alliances again. The admin channel also got the same partial message twice.

- **What changes.** A re-run without force of a snapshot that has stale rows (read, no error, `is_fresh = false`) is refused with 409 `snapshot_stale` and `stale_count`. /admin then asks "{count} alliances in this snapshot are stale. Read them again? About {count + 1} API calls." On yes it sends `stale=1`: the claim deletes every row with `is_fresh = false` (the failed rows are among them) and their members, and the run reads those alliances again. Fresh rows are kept. On no, nothing runs.
- **`stale=0`** keeps the stale rows: the D62 re-run (failed and missing alliances only). The route accepts it for callers that do not want the question.
- **Not after a scheduled event has started, for Before.** Read once the event is under way, a roster already counts kills from the event, and the before/after delta would be wrong. From `events.event_at_utc` on, `stale=1` on a scheduled Before answers 409 `event_started`, and a Before press without `stale` keeps the stale rows (the D62 re-run) instead of asking. Manual events (D28) and After snapshots have no such limit.
- **Cost:** 1 quota call plus one per alliance read. The budget check is unchanged. A re-read helps only if the upstream refreshes again; it can come back stale, and the snapshot stays partial.
- **One admin message for a phase whose event message was just posted.** D31 posts a second message when a run is not complete, because an edit does not notify. When the event's admin message was posted by this run (the first phase, or the old message was gone), that post already notified, so the second one is no longer sent. An edited message still gets its own post.
- **Workflow dispatch** (`tick.yml`, phase before/after) calls the route without `stale`, so on a snapshot with stale rows it now gets 409 `snapshot_stale`. The workflow is unchanged.
