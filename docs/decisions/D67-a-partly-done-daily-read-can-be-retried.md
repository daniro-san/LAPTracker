## D67 — A partly done daily read can be retried, and a retry keeps the rosters already read (2026-11-16, owner, 08zzzw)

Why: the daily read of 2026-11-16 closed `partial`: 7 of 20 alliances failed with `v1.schema` (the parser, fixed in 08zzzv). D60's Retry took only a `failed` day or one left `running`, so `/admin` could not read those 7 again and their rosters for that day stayed missing. The owner: let the admin run a full retry of a day.

- **Which days.** Today's read (the server day) can be retried when its status is `failed` or `partial`, or when it was left `running` for at least `RUN_STALE_AFTER_MS` (150 s). A `complete` day, a day with no read and a read `running` for less than 150 s still answer 409 `daily_read_not_retryable`. A past day is never retried: the upstream returns only the roster as it is now, so no later read can be that day's roster. The member history never reads `read_day`; it shows each roster at its own `source_updated_at`. A read made later and stored under the past day would therefore leave the gap in the history as it is, and only make `/admin` call that day done with rosters of another day. A gap is not an error in the history: the next roster is compared with the last usable one, and its card names the span.
- **What it reads.** Every roster in `DAILY_ROSTER_IDS` again, not only the ones that fell short: 1 + k calls (21). The budget rule, the 100 s deadline and the call cap are D60's.
- **What it keeps** (INVARIANT `daily-read.retry-keeps-rosters`). D60's retry deleted every row of the day at the claim. On a `partial` day that would throw away the rosters already read before the new read has one to put in their place: a retry during an outage, or one the quota rule stops, would leave the day with fewer rosters than before. So:
  - at the claim, only the day's error rows are deleted (`reclaimDailyRead`);
  - a roster the retry reads replaces the day's earlier roster of that alliance (`storeDailyRoster`, one upsert on the day and the alliance);
  - an error row is stored only when the day has no roster of that alliance;
  - an alliance the retry never reached keeps the roster it had, or has no row.
- **The outcome is the day's, not the attempt's.** After storing, the status, the failed list and the stale list are read from the day's rows (`dailyRosterStates`). For a first read the day's rows are that read's rows, so nothing changes.
- **A kept roster that is old counts as stale in the day's outcome** (owner, 2026-11-16: a kept roster could be hours older than the others and the day still closed `complete`). The rule is the existing one (INVARIANT `freshness.20-min`) applied to the day: a roster more than 20 minutes older than the start of the day's latest read is stale. So a day is `complete` only when every roster is at most 20 minutes older than that start; a day with an older kept roster is `partial`, names that alliance as stale (the retry's answer, `/admin/runs`: `○ [TAG] stale`), and can be retried again. The alliance's failed call shows in the read's calls table and log. The stored row is not changed: its `is_fresh` stays as it was when read, so the member history keeps showing that roster, at its own time. `/admin/runs` derives the mark from `source_updated_at` and `daily_reads.started_at` (`problemsOf`); there is no new column.
- **`/admin`.** The Retry card under "Run something now" also shows for a partly done day, with its own sentence. The confirmation says a roster already read today stays if its new read fails.
- **Discord.** The admin line of a `partial` day ends with `[Retry on /admin ↗] · [Daily reads ↗]`; a `failed` day keeps `[Retry on /admin ↗]`.
