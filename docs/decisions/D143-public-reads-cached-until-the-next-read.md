## D143 — The public pages' reads are shared until the next write, and a page whose database does not answer says "Data temporarily unavailable" (2026-11-21, issue 521, perf Batch 4; amends D79, D141)

Why: every view of a public page read the same rows from Neon, and those rows change only when the tick, a run, a details lookup or an admin writes. Each view woke the compute. Measured before this change (local production build, invented data): `/alliances` 12 statements a view, `/players/[uid]` 14, `/` 18. With the database down, every public page answered "Something cracked."

**What is shared.** `lib/public-cache.ts`, modelled on `lib/event-cache.ts` (D79): Next's `unstable_cache`, one tag `reads`, the deployment id (`VERCEL_DEPLOYMENT_ID`, else `local`) in the key because Next's data cache outlives a deployment on Vercel, and `revalidate` of 1 h as a safety net. Reached only through `AppContext.publicCache`; tests get `memoryPublicCache()`. Each loader opens its own connection (`withOwnDb`), never the request's (D141, Batch 3). The reads (`app/_ui/public-reads.ts`):

- `events`: `listEvents`, the header of every public page and the input of `homeEvent`. `homeEvent` itself runs per request (it depends on `now`); `getEventPage` takes the list as a parameter.
- `alliance-list`: `allianceList` for page 1, and for the page asked once it is clamped to the pages there are (a made-up `?page=` adds no entry). The ledger's "All alliances" link counts from page 1's entry.
- `event-alliances`: `eventAllianceIds`.
- `player`: `playerHistory` and `playerProgress` of one uid. `player-search`: `/players?q=`, keyed by the lower-cased text (`ILIKE` finds the same players for every case).
- `alliance-history`: the first page of `/alliances/[id]/history` (no `before`) with its board line, per filter; `statement`: `allianceStatement`. Both keys hold the time of today's details lookup, see below. An older page (`before` from the URL) is read per view.
- `upstream`: `upstreamRows`, the banner's rows with no `now` in them. "Down" is computed per request by `upstreamStatusOf(rows, now)` (D27), so a kept row turns "down" when a run never closes and stops after 24 h with no new write.

**Not shared.** Desk and private data (D71) and every blocked roster field: the loaders are the public read models that already serve these pages, with photos as `hasAvatar`/`frameId` only; no D76 aggregate is among them. "Get today's details" (`detailsState`) is read per view: it depends on the clock, the day's lookup claims and the workspaces' sealed keys. The rest of the event pages (event detail, names, ranks, roster changes, movers, End turnout) is one shared entry since issue 538 (see the amendment below).

**Values.** Stored as JSON text. Deviation from the spec's "JSON values only, no Date": the loaders return `Date`s, so `encode` writes each as `{"$date": ms}` and `decode` gives it back as a `Date`; a `Map` or `Set` throws instead of becoming `{}`. A `null` (unknown uid or alliance) is never kept, so a crawl of ids leaves no entries. One read per key at a time in an instance (single flight). `invalidate` clears the in-flight reads, so a view after a write does not join a read that began before it, and bumps a generation: a read that ran across an invalidation is served to its own view and not kept (QA reproduced a slow miss straddling a write that kept the old rows).

**Invalidation** (INVARIANT `cache.write-invalidates-reads`). `ctx.publicCache.invalidate()` (`revalidateTag("reads", { expire: 0 })`) right after every write to `daily_rosters`, `alliance_board`, `alliance_snapshots`, `member_snapshots`, `events`, `snapshots`, `tracked_sets`, `alliances` or `player_frames`:

- the tick, in its body: the day's tracked set when it creates it, the daily read and its automatic retry, and the scheduled event row when it creates it (`findOrCreateEvent` now says `created`);
- `POST /api/daily-read/retry`; `POST /api/alliances/[unionId]/details` (done or failed); `POST /api/snapshot` when it created the scheduled row;
- `lib/run.ts`, beside `eventCache.invalidate`, after every run that claimed a row, samples included;
- `POST /api/manual-event`, `/rename` and `/settings`.

A write that throws part way invalidates too, since its rows may be partly written, except when the database is down: the kept pages are then all the public site has. Not invalidated: rehearsals (never public), Discord message ids and the Friday check's claim (never read by a public page). `lib/public-cache.test.ts` reads the source like the OCR routes' check: every function that writes those tables reaches a route or page only through a module that calls the invalidation.

**Timing on Vercel.** Next applies a `revalidateTag` after the handler returns (`waitUntil`). So an invalidation in the middle of a run does nothing if the function is killed; this change does not invalidate at a run's claim. A function killed mid-run leaves the shared reads up to 1 h old, until the next write. "Get today's details" refreshes the page as soon as its answer arrives, which can be before the tag is applied: the history and statement keys hold the time of today's lookup, so the finished lookup changes the key and that view reads the new roster.

**Bounds this accepts.** In another instance than the writer's, a read that began before a write and ends after the invalidation is kept as fresh until the next write or the hour; the window is one read, about 100 ms. `/players?q=` keeps an entry per text searched (at most 64 characters). A miss opens one connection per shared read, more sessions than before on the first view after a write.

**Database down.** `lib/data-unavailable.ts`: `databaseDown(error)` is true for Postgres class 08, 53300 and 57P01–57P03, the `ECONN*`/`ETIMEDOUT`/`ENOTFOUND` codes, the driver's connect-timeout and terminated messages, and the Neon driver's WebSocket error event, also when Drizzle wraps them. `withPageDb` and `withOwnDb` rethrow such an error as `DataUnavailableError` with the digest `data-unavailable`, which Next keeps to the client, and `app/error.tsx` then shows "503 · Data temporarily unavailable. The ledger can't be read right now. Nothing is lost. Try again in a few minutes." (`lib/copy-errors.ts`, every public language) instead of "Something cracked." The HTTP status stays 500 (Next sets it for a thrown render). Pages whose reads are all shared keep answering from the cache: `/alliances`, `/players`, `/players?q=`, `/players/[uid]`, and since issue 538 `/`, `/events/[id]` and the history page (see the amendment below); an expired entry is served while its refresh fails. A page whose entry is not in the cache shows the 503 page. A page's read waits at most 10 s for a connection (`PAGE_CONNECT_TIMEOUT_MS`), on the request's Pool and on `withOwnDb`, then the page says the data is unavailable instead of hanging. On the request's Pool the driver also counts the wait behind the request's other reads; the widest page's 51 statements take about 0.1 s locally.

**Uptime.** `uptime.yml` keeps `/w/request` (private, never cached) as its database probe; `/alliances`, and since issue 538 `/`, now check the site, not the database.

**Amendment (2026-11-21, issue 538): the event page's reads are one shared entry.** `getEventPage` (`lib/queries/event-page.ts`) reads the event's detail, alliance names, ranks, roster changes, member movers, war turnout (also "so far") and kill share vs might share in one loader, kept under `event-page` with the key `[event id, war-turnout flag, kill-vs-might flag]`. The three Maps go as their entries and are rebuilt per request. `homeEvent` stays per request. An id that is not in the shared event list (the same `publicEvent` filter as `getEventDetail`) answers "no such event" with no read, so made-up ids leave no entry and cost nothing. No new invalidation: `lib/run.ts` already invalidates `reads` after every run that claimed a row, samples included. Measured (local production build, invented data): repeat views of `/` and `/events/[id]` went from 10 statements and 3 sessions to 0; the first view after a write costs 26/9 against 25/8. The entry of a 20-alliance event is about 30 KB, far under Next's 2 MB item limit. `withOwnDb` now opens at most 3 connections, like the request's Pool, because this loader runs 6 queries at once.

What this accepts:

- War turnout "so far" was a D79 event-cache entry with a 60 s bound (`turnout-so-far`, now removed). It is now bounded like every shared read: the next run's invalidation, else 1 h. So a run killed after it wrote can leave it, and the rest of the event page, up to 1 h old, or until the next sample's run (15 min) during an event.
- The public event page's "Updating now" chip is generally not seen while a Start or End run goes: the cached page shows the state from before the run until the run's invalidation is applied, after the run's handler returns. Invalidating at the claim would not help, for the same reason. A killed run leaves the pre-run state (up to 1 h) instead of turning "failed" from `now`. The panel's product, user and adversarial personas accepted this; showing it again would need a small per-view read of the running row (one statement a view).
- In another instance than the writer's, a read that straddles a write can be kept until the next write or the hour, as for the other shared reads.

The history page with the database down: `detailsState` that cannot reach the database is unknown (null), so the page is served from the shared reads with no "Get today's details" and no "Read every day" line, and the statement falls back to none on a miss. When today already had a lookup, its key is unknown then, so the page still shows the 503 page. `uptime.yml`'s database probe is `/w/request` only: `/` and `/alliances` are served from the cache between writes.

`lib/event-cache.ts` (D79) gets the same instance fixes as this cache: its in-flight map and an invalidation generation sit on `globalThis`, an invalidation drops the event's in-flight reads, a finished read removes only its own in-flight entry, and a read that ran across an invalidation is served once and not kept.

**Amendment (2026-11-21, issue 473).** The `events` entry also holds, per event, whether it has a usable 15-minute sample (`sampled`, the header's fight clock link): `sampledEventIds` runs beside `listEvents` in the same loader. The `event-page` entry also holds the previous chain event's totals per alliance (`previousEventTotals`), for the ledger's "since" line. No new invalidation: both change only with a run, and `lib/run.ts` already invalidates `reads` after every run that claimed a row. The compare page's header now reads the shared event list too. `player-search` matches carry might and level (public roster fields) and list names that start with the text first; `alliance-history`'s first page carries each card's counts.
