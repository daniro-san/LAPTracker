## D69 — Event samples: a reading every 15 minutes between an event's Start and End (2026-11-16, owner, 08zzzza, issue #279)

Why: the owner wants charts of the busiest moments of an event (heatmaps, who fought when) to plan who joins when. An event has only a Before (Start) and an After (End), so nothing shows when anything happened. Spike #183 (Option B, 08zzh) designs samples, windows and schedules in one build that rewrites every Start/End reader; that is too large before the KvK of Saturday 2026-11-21. This is build 1a: samples for single-window events, with Start and End unchanged, so data starts being collected now.

- **Shape.** A sample is a `snapshots` row with `phase = 'sample'` and `slot_at` (the slot instant, UTC; null on a Before or an After). Its alliance rows are `alliance_snapshots` rows with the members as D60's parallel arrays (`member_uids`, `member_names`, `member_power`, `member_kills`; a null power or kills stays null, D15). No `member_snapshots` rows and `raw_json` null, so a sample never stores a blocked roster key. An error row has no arrays. Migration 0017. Measured on the review (08zzh): ≈ 63 KB per sample of 20 alliances with names.
- **Constraint.** D1's guarantee is kept: `snapshots_event_phase_unique` becomes a partial unique index on `(event_id, phase) where phase <> 'sample'` (one Before and one After per event, as before), and `snapshots_event_slot_unique` is a partial unique index on `(event_id, slot_at) where phase = 'sample'`. A check ties `slot_at` to the phase. The insert of a sample is its claim (`on conflict do nothing`), so two ticks in one slot cannot both take it (INVARIANT `sample.once-per-slot`). Why two partial indexes and not one `unique nulls not distinct (event_id, phase, slot_at)`: each rule reads as its own guarantee, the Before/After rule keeps its name and meaning, and the slot index is already the shape the window build needs (`(window, slot_at)`). The cost: an insert's `on conflict` must name the index's predicate (`lib/repo/snapshots.ts`).
- **Slots and the tick.** `SAMPLE_EVERY_MIN` (env, default 15, 0 = off, must divide 60) sets a grid from the hour: :00, :15, :30, :45. A slot is due from its instant until the next one. An event (scheduled or rehearsal, never a manual round, INVARIANT `tick.skips-manual`) is sampled at a slot when the slot is strictly after its `before_at` slot and strictly before its `after_at`, its Before has finished (any status but `running`), and it has no After row. The tick's order is unchanged with one step added: create the scheduled row, then a due phase (Before and After always win), then a due sample, then the Friday check, rehearsals and the daily read (D21's one action per tick; a tick that runs a phase never samples). The tick passes the slot that holds now, so a missed slot is never caught up. Sampling stops once the After has a row.
- **Collector.** `runSample` reads the event's alliance list (the one the Before stored, INVARIANT `event.after-uses-event-copy`) through the same `/v1` path as a phase: `?fresh=1` (D64), the 502/503/504 retries, the 100 s deadline (D25), `MAX_UPSTREAM_CALLS`, a 429 stops it. No ranks board and no internal fallback (D5 covers Before and After): a failed alliance gets an error row, as the daily read does. A stale row is stored with `is_fresh = false`, which makes the sample `partial`. A sample writes `run_logs` under its snapshot id, so `/admin/runs` lists it as its own run ("Sample 10:15") and links the same run page. A sample does not update `player_frames` (D66); the Before and After do.
- **Budget** (INVARIANT `budget.samples-yield-to-after`). Before a sample, `remaining ≥ sampleQuota(n) = requiredQuota(n) + 1 + 4n`: the After's reserve plus the sample's worst case (its quota call and every read retried 3 times), 131 for 20 alliances. Below that the sample is skipped: its row closes `failed` with `quota: remaining … < required …` and a `quota` log line. After any sample at least `requiredQuota(n)` remains, which is what the After needs to start, so the middle samples always give way first. `dailyReadQuota` is unchanged: the daily read is skipped on a scheduled event's day (D60), and a rehearsal's one or two samples cost about 21–42 calls on its day.
- **Readers.** Every read of an event's Before and After filters samples out with one predicate, `phaseSnapshot` in `lib/queries/visibility.ts` (INVARIANT `queries.phases-not-samples`): the event page and `GET /api/events*` (`listEvents`, `getEventDetail`, so compare D57, the event picture D58 and the public Discord message too), alliance pages and alliance history, names, ledger ranks history, the upstream banner, member history (`eventUsable`: a sample has no member rows and would read as a 0-member card), the admin target and rehearsal panels, the rehearsal verdict, `scheduledEventDone` and the event's admin message blocks (`listPhaseReports`). Readers that join `member_snapshots` (player pages, search, movers, rosters) never see a sample. Only `eventSamples` and the admin run lists read samples.
- **Read model.** `eventSamples(db, eventId)` (`lib/queries/samples.ts`): a public event's readings in time order, Start (at `before_at`), the samples (at their slots), End (at `after_at`); per alliance the read time, the fresh flag, might, kills, members, and the roster as `{uid, might, kills}`. A reading still running or with no usable alliance, and a failed alliance row, are left out. No page uses it yet.
- **Discord.** No public message for a sample. On the admin channel the first sample of an event that ends `partial` or `failed` posts one message (the event's name, the sample's run block, a link to `/admin/runs`); later samples of that event that fall short post nothing (INVARIANT `notify.sample-once-per-event`), so an outage is one message per event, not one per sample. The event's own message (D31) is not edited by a sample. Skipped rather than edited because an edit does not notify (D31) and the run list already holds each sample.
- **Why Start and End stay as they are.** Every existing reader (37 files on dev quote a phase) keeps its output with one filter each, and the Before and After keep their member rows, `raw_json`, ranks board and internal fallback. The rewrite of those readers is the window build's work.
- **What the window build changes.** An `event_windows` table (event, start, end, cadence); a sample then belongs to a window, and `(window_id, slot_at)` replaces `(event_id, slot_at)` (every sample already knows its event and slot, so the backfill is one window per event). A window's first and last samples become its Start and End, so Origin of Chaos (two windows, next on 2026-12-05) gets a Start and End per window; readers move from the `before`/`after` phases to the windows; the budget rule reserves one After per window end still due that UTC day; the admin message gets one edit per window end. Schedules from `/admin` and the charts are later builds (charts on D68's SVG components).

- **Amended 2026-11-16 (review).** The not-a-sample predicate is defined once, as `phaseSnapshot` in `lib/repo/snapshots.ts`; `lib/queries/visibility.ts` re-exports it, so one grep for `phaseSnapshot` finds every reader of the Before and After, in `lib/queries` and in `lib/repo` (`scheduledEventDone`). A row already in memory is tested with `isSample(phase)`, next to it (`loadVerdictInput`, `listPhaseReports`, `eventSamples`). `eventRanks` filters with `phaseSnapshot` in SQL, so a sampled event no longer loads its sample rows on the event page, compare or alliance-in-event pages.

- **Amended 2026-11-16 (Saturday hardening).** Measured on 2026-11-16: a live `?fresh=1` read takes about 1.5 s, 3 of 18 reads in a 48-minute probe hung until the client timeout, and AFR and URSA answered 502 repeatedly. cron-job.org abandons the tick at 30 s and notifies after 2 failures (D30), and the tick awaits the whole run, so a sample must end before 30 s. (1) `SAMPLE_CALL_TIMEOUT_MS = 12_000` is each call's timeout in a sample (the quota call too); a Before and After keep the adapter's 30 s (`CallOptions` on `V1Source`). `SAMPLE_DEADLINE_MS = 25_000` is a sample's run deadline in place of D25's 100 s: alliances not read by then are named `not fetched: deadline` in the run's summary, as in a phase, and the sample closes `partial`. `SAMPLE_NOTIFY_CAP_MS = 28_000` cuts the one admin message when the response would pass 28 s. (2) An alliance with an error row in any earlier sample of the same event is read once, with no retries, in the later samples of that event (INVARIANT `sample.failed-reads-once`; `failedSampleUnionIds`, one query over the event's sample rows), so a persistent 502 does not spend its retries and the deadline in every sample. A Before or After's failure does not count. `sampleQuota` is unchanged: the deadline and the no-retry rule only lower a sample's worst case, never raise it. Release rules: (a) release migration 0017 only at a day and time when no Before, After or manual round can be claimed: the previous build's `onConflictDoNothing({ target: [eventId, phase] })` cannot match the new partial index, so between the build's migrate step and the new deployment taking traffic, or after a rollback, a claim would fail; (b) never roll back production below migration 0017.
