## D97 — The thefts log: Secret Operations thefts per attacker, a follow-up per attacker, no list of our members (2026-11-16, owner, 11j, issue #321)

Why: in Secret Operations, players can take a member's quest rewards. The leadership warns the alliance and talks to the other alliance's leaders when a player of our own server does it (issue #321). Until now this was kept in chat. This adds to D71 (the workspace), D74 (the screenshot reader) and D75 (people first).

- **What an entry is.** One theft per row in `thefts`: when (the report's server time as an instant; null when the time was not read), the attacker (name and alliance tag, and the uid when the player is in a tracked alliance's roster), what was taken (`quest_rewards`, or null when it is not known: a report line whose sentence was unreadable, or an officer who chose "Not known"), the member it was taken from (uid and name from the workspace's own newest roster; null when not given), the source (`typed` by an officer, or `photo` from the screenshot import), an optional note, and who added it and when. Every row has `workspace_id`. Migration 0023 creates `thefts` and `theft_follow_ups` (`lib/schema-thefts.ts`).
- **Who the attacker is.** `attacker_key` is `uid:<uid>` for a player found in the newest daily roster of one of the tracked alliances, else `name:<name key>` (D74's `nameKey`). Entries with the same key are the same attacker. The attacker's alliance is the tag of their newest entry, so a player who moved shows once, under their latest alliance.
- **Finding attackers reads public data.** The attacker search and the import's attacker match use `lib/queries/server-players.ts`: the uid, name and tag of every member of each tracked alliance's newest usable daily roster, from the member-history arrays only (never `raw_json`). These are the names public pages already show. `lib/private` does not read other alliances' rows of the shared roster tables itself (D71's tenancy rule). The workspace's own alliance is left out of the search.
- **Counts.** Per attacker and per attacker alliance: this week (the game week, Monday 00:00 to Monday 00:00 server time), in total, and the last time. An entry whose time was not read counts in the total only. Alliances and attackers are listed with this week's count first, then the most recent, then the total.
- **No list of our members (D75).** The page lists attackers, never victims. How many times a member was taken from appears only inside an attacker's card, with the members sorted by name ("Taken from: Commerage (1) · Seesky (1)"). There is no ranking of our members anywhere.
- **"Talks with their alliance" per attacker** (named apart from the Follow-up tab). Three states: open, talked to their leaders, resolved. Every change is a new row in `theft_follow_ups` (state, note, who, when); the newest is the state, and no row means open. A theft whose time is after the newest change shows the attacker as "Open again", with one sentence ("Ana marked this “Resolved” on Fri, Nov 13. A new theft came after that, so it is open again."): talking or resolving was about the thefts before it. Older changes are listed under "Earlier". Save stays off until the state or the note changes, so the history holds no repeated rows. A theft without a time does not reopen. The future Follow-up tab (issue #340) reads the same rows.
- **The screenshot import's save hook.** `saveSecretOpsDraft(db, access, draft, clock)` (`lib/private/thefts-import.ts`) takes a reviewed "Secret Ops report" draft: the member whose report it is, when the picture was read (the year of the report's `MM-DD HH:MM` comes from it; a date after the reading day is from the year before), and the entries as `parseSecretOpsReport` gave them or as the officer corrected them.
  - `kind: "help"` is left out; `kind: null` is saved with what was taken unknown.
  - An entry naming the workspace's own alliance (its tag, or a name that matches exactly one member) is left out: members help each other, and a help line whose sentence was lost must not become a theft by one of our members.
  - The attacker is matched to a tracked player only when `matchName` finds exactly one and the read tag, if any, is that player's; otherwise the name and tag are kept as reviewed.
  - Saving the same report twice adds nothing: each (attacker, member, time) is saved only as many times as the log does not already hold it. Two thefts in the same minute in one report are both kept.
  - An entry without an attacker name refuses the whole draft (`attacker_missing`), and a member who is not in the alliance refuses it (`not_in_alliance`).
- **Typed entries.** The attacker is a tracked player of another alliance (picked from the search), or a name typed with an optional tag (1 to 32 characters). Saving the typed name is offered at once only when the search finds no one, else behind "Not in the list?", because a typed name is a separate attacker from the listed player. The time is the report's server day and time and cannot be later than now (one minute of grace). The member is picked from the alliance's newest roster through the name matcher and the roster search. An entry can be removed (two taps); there is no edit in place.
- **Game terms (D52).** French uses the report's own words ("Opération secrète", "récompenses de quête"). No Portuguese game text has been seen, so Portuguese keeps "Secret Operations" and "Quest rewards" in English until the owner gives the game's words.
- **Not built.** Per-incident steps (reported, warned, retaliated), the attacker's server from the "Info de Docteur" card, links to the attacker alliance's public page and leader, and the ready-to-paste warning message: issue #321 lists them, the session's scope did not.

**Amendment (owner, 2026-11-17): a theft has a type, not "what was taken".** The owner asked for the add sheet's "What was taken" (options "Quest rewards" and "Not known") to become a select of four types. This replaces the "what was taken" part of "What an entry is", the `kind: null` line of the save hook and the "Quest rewards" part of "Game terms":

- **The field.** "Type" ("Tipo", "Type") is required on the add sheet, a select of Tile hit, Ops, Caravan and Sanctuary. The four labels are game terms and stay in English in all three languages (D52). The strings "Quest rewards" / "Récompenses de quête" and "Not known" / "Não sei" / "Inconnu" are gone from the dictionaries.
- **The data.** `thefts.kind` (`tile_hit`, `ops`, `caravan`, `sanctuary`; null only on rows saved before the type was asked) replaces `thefts.stolen`. The migration sets `ops` where `stolen` was `quest_rewards` (Secret Ops takes quest rewards) and leaves null as null. The route refuses any other value (zod enum). The migration drops `stolen` in the same release, so for the few minutes between the migration (it runs before the build) and the new build going live, the old build's thefts page and Secret Ops saves fail. Accepted for a page a handful of officers use; ship it outside event hours.
- **The screenshot import.** `saveSecretOpsDraft` saves every kept entry as `ops`, an entry whose sentence was unreadable (`kind: null` from the parser) too: it came from a Secret Ops report. Help is still left out.
- **Display.** An entry's line reads "Taken from Marigold · Ops"; a row without a type shows "—" (D75: missing data is not a fault). The alliance and attacker counts are not split by type.
- **Not changed.** The page title ("Secret Operations thefts"), its lead ("took quest rewards") and the glossary's "theft" still describe Secret Operations only; the owner has not said whether they should name the other types.
