## D15 — A null member `kills` or `power` stays null and sums as 0 (2026-11-04, Session 2, plan Phase 2)

`/v1` sends `kills: null` for some members: one in AFR (`fixtures/v1-ids/67111040.json`) and two in FGH (`fixtures/v1-ids/67111128.json`). The adapters keep `null` on the member row, so "unknown" is not stored as "zero kills", and `sumKills` (lib/compute.ts) counts it as 0, so `total_kills` is still a number. The UI shows `—` for that member. `power` gets the same rule, although no fixture has a null `power` yet. Cost: an alliance total can rise between BEFORE and AFTER only because a member's `kills` went from `null` to a value. That is a real but rare distortion. Marking the whole row unusable over one member would lose the alliance instead.

- **Amendment 2026-11-22 (drilldown batch B, D83 amendment).** The alliance page's "± Kills" order ranks a member in both rosters by the gain War turnout counts, a null as 0, so the gainers War turnout counts come first. The member's change still shows `—`. A member with a null at Start and a value at End therefore sorts by their whole End kills.
- **Amendment 2026-11-22 (issue 692, persona panel).** On the alliance page's member list, a member in both rosters whose kills are unknown on one side keeps `—` for the change and says why after it: "Start unknown" or "End unknown" (`members.startUnknown`, `members.endUnknown`). While the list is sorted by ± Kills, the note adds "counted as 0" (`members.countedAsZero`), because that order counts the unknown figure as 0. No gain is shown for such a row: the order's number is never written as a read change. A member unknown at End ranks as a fall of their whole Start kills (`killsGain`, End as 0): below a smaller read fall, above a bigger one. Rejected: showing the gain the order used (`+2.1M` with a note), because the panel's alliance leader read it as a real gain to reward; and one note under the list, because nobody reads it within the first screen. PGlite tests in `app/_ui/member-drilldown.test.ts`.
