# D84 — The merge simulator: two alliances against the member cap, public, totals only (2026-11-16, owner, 08zzzzl, issue #282)

Why: merge decisions come while alliances empty (URSA emptied 2026-11-07..11; BOH went from 67 to 31 members on 2026-11-16). IMPA + BRAV would rank first with all 182 members (5.18 B) but sixth within the cap (3.99 B, 82 members and 1.20 B left out). The raw sum misleads, so the page shows both.

- **Owner decision (2026-11-16).** Public, alliance-level arithmetic only, never a member name, neutral wording, labelled hypothetical ("Simulation, not a plan"). Nothing is posted to Discord.
- **Page.** `/alliances/merge?a=<union_id>&b=<union_id>`: a GET form with two selects of the tracked alliances, no client-side fetch, the URL is the link to share (as `/events/compare`, D57). The alliance page's title row has "Simulate a merge", which opens it with `a` set. A malformed id, or one that is not a tracked alliance with a usable roster, is a 404; a missing one waits in the picker; the same alliance twice shows "Pick two different alliances."
- **Which cap.** The cap is not a fixed 100: the API says 100, yet CR8R had 108 members and NDA 101 on 2026-11-16. The merged alliance gets the larger of the two stored capacities (`alliance_snapshots.capacity`, D32; each alliance's newest public row that has one). When neither has one, 100 (`DEFAULT_CAPACITY`) is assumed and the page says so. The larger of the two is the reading most favourable to the merge; owner confirmed 2026-11-16: the larger of the two stored capacities stays.
- **Who is within the cap.** The members are merged by uid (a member in both rosters counts once, at the larger might, since the two readings may differ in time); the strongest by might fill the cap, a tie going to the lower uid. A null might counts as 0 (D15). "Left out" is `max(0, members − cap)`. The page says the rule in one sentence (`merge.rule`) and shows "N over the cap of C" when members exceed it.
- **Which roster.** Per alliance the newest usable roster (fresh, no error, not empty, as the member history reads them, D60) across the daily reads and the public event Before/After rosters, by `source_updated_at`; the daily read on a tie. Recency decides because a daily read exists every server day, so it normally wins, and an event roster wins only when it is newer (a failed or stale daily read leaves a gap). The rank is against the other tracked alliances' might from the same rule, so two alliances can be read at different times (the page shows each side's "as of"). The rank counts alliances with strictly more might than the merged one, so a tie ranks the merged alliance ahead.
- **What it shows.** One sentence first (`Together: #1 with everyone, #6 within the cap of 100`; when all members fit, one rank and "All N members fit"). Then HTML bars (D68): members against the cap (a marker at the cap, the part over it in the seal colour), might (each side, together with everyone, within the cap, the part that would not fit), the two ranks, each side's latest war turnout (`memberTurnout`: members who gained kills of those in both rosters, in the newest of the last 3 events with a Start and an End), and each side's "as of".
- **Privacy.** The read selects an alliance's tag, name, badge, capacity and might, and each member's uid and power. It returns no member, name, kills or blocked roster key; the member list stays inside the query and `lib/merge.ts`, which returns counts and sums.
- **Code.** `lib/merge.ts` (pure: `simulateMerge`, `mergedCapacity`, with a property test), `lib/queries/merge.ts` (`mergePage`, PGlite tests), `app/_ui/MergePicker.tsx`, `app/_ui/MergeSimulator.tsx`, `app/(pages)/alliances/merge/page.tsx`. Words in `lib/copy-merge.ts`, translated in the 17 languages (D48).
- **Not done.** No what-if edits of single members, no more than two alliances, no saved or shared simulations beyond the URL, no Discord message.
