## D71 — A private workspace per alliance: Discord sign-in, every roster field for its own leadership (2026-11-16, owner, 11a, issue #303)

Why: the owner wants a private area where an alliance's leadership sees everything the game API returns about its own members, not only the public stats. Owner answers (2026-11-16): sign in with the Discord account and the alliance's leadership role; "capture everything and show everything possible", to that alliance's leadership only; no extra API calls. The owner also asked how this works for other alliances; see "Other alliances". Issues: umbrella #293; this decision #303; end-of-day read #294; sign-in #295.

- **Name.** The private area is a **workspace** (glossary). "Leadership" already means the R5 and R4 roles in `lib/queries/leadership.ts`.
- **Who: sign-in.** Discord OAuth with scopes `identify guilds.members.read`. After the code exchange the server calls `GET /users/@me/guilds/{guild_id}/member` with the member's token. Access is granted when the member's role ids intersect the workspace's `leader_role_ids`, or when the Discord user id is on the workspace's allowlist. No bot joins the Discord server. No new dependency: two `fetch` calls, `node:crypto` and `secretEquals` (`lib/auth.ts`). `DISCORD_CLIENT_ID` and `DISCORD_CLIENT_SECRET` are optional, so the app starts without them; the secret joins the log redaction list. The Discord server id and the role ids live in the database, so a new alliance needs no deploy.
- **Who: sessions.** The cookie holds a random 32-byte token: HttpOnly, Secure, SameSite=Lax (the OAuth callback arrives cross-site), 7 days. The database stores only its sha256 (`workspace_sessions`), so access can be revoked at once. The OAuth `state` is in a separate 10-minute cookie, compared in constant time. Roles are checked again at each sign-in. Writes go through route handlers only and require Origin equal to the app origin, `Sec-Fetch-Site: same-origin`, a JSON content type and a valid session; the rate limits reuse `auth_attempts`. `/admin` and its PIN (D3) are unchanged.
- **Who: tenancy.** Every private table has `workspace_id NOT NULL`. Private queries take a branded `WorkspaceAccess` value that only `requireWorkspace(slug)` creates, and the workspace id never comes from a request. A two-tenant PGlite test must show that one workspace cannot read another's rows.
- **Who: the fence.** Private code lives in top-level `lib/private/`, not in `lib/queries/private/`: `lib/queries/blocked-keys.test.ts` scans `lib/queries` non-recursively, so a subfolder would escape it. An `import-x/no-restricted-paths` zone forbids importing `lib/private` from `app/(pages)`, `app/_ui`, `app/api`, `lib/queries`, `lib/notify*`, `lib/discord-*`, `lib/logger.ts` and `lib/run.ts`. Private pages and handlers sit under `app/(private)/w/[slug]` and `app/(private)/api/w/[slug]`; the URL is `/w/[slug]`. Logs written by `lib/private` carry codes and counts only.
- **Leadership only** (owner, 2026-11-16). Only the alliance's leadership uses and edits the workspace. That includes the notices library: event notices, rules and strategies, sometimes with images, which the leadership posts today on the in-game notice board, in in-game mail and on Discord.
- **One level of access** (owner, 2026-11-16). Every leadership member (R5 and R4) can view and edit everything in their alliance's workspace. There are no per-person permissions inside a workspace.
- **Regular members are out of scope** (owner, 2026-11-16). Anything for non-leadership members needs its own decision later; the owner says it "has to be thought through carefully". Issue #301, the member self-report link, is deferred on that basis.
- **Other alliances.** The owner registers a workspace on `/admin` (PIN): the union id (it must be in `ALLIANCES`), the Discord server id, the leadership role ids and a slug. No deploy. Later, self-service (issue #302): the alliance's R5 proves ownership by putting a one-time code in the in-game alliance declaration, which `/v1/alliances/{id}` returns as `declaration`. Until then only the owner registers one.
- **What it shows.** Every roster field the API returns for the alliance's own members: `daily_tech`, `daily_honor`, `active`, `joined_at`, `online`, `last_online_at`, `x`, `y`. Only that alliance's workspace sees them, only its signed-in leadership. `daily_tech` is "tech points donated today" and `active` is "weekly activity" in the API docs. The photo still reaches pages only as the image `/img/avatar/[uid]` serves (D22); `avatar_url` is never returned.
- **Languages** (owner, 2026-11-16). The leadership of OGs has people who read only English, only Portuguese or only French; today they use a Discord translation bot and the game's translations. The workspace is therefore not English-only: D48's rule that `/admin` stays English does not apply to it. Its pages use the public pages' language mechanism (a dictionary per language, `lib/copy.ts`, `lib/i18n/<tag>.ts`, D48), with `en`, `pt-BR` and `fr` required first. Text that officers write (notices, notes) is shown in the reader's language by machine translation; the original is one tap away, and a fluent officer can correct a translation.
- **Open for the owner: the translation service.** It is decided together with the screenshot import (issue #299, an external processor through the AI Gateway). This decision picks none.
- **What stays as it is.** Public pages, public routes, Discord messages, `run_logs` and `app_errors` are unchanged. `BLOCKED_ROSTER_KEYS` (`lib/queries/blocked-keys.ts`) is unchanged and still binds `lib/queries`, every route, page, log and message outside `lib/private`. The hard rule in CLAUDE.md now allows `lib/private/` code to return those fields to its own alliance's workspace.
- **Supersedes.** Plan §12.6, "No user accounts, no OAuth", for the workspace only; the rest of the site has no accounts. It is the story §12.6 said §12.2 would need when the alliance stores anything private (Discord ids). It also changes §12.1: the blocked fields are served to the workspace.
- **New stored data.** Discord user ids and display names of the people who sign in (and their session hashes); member facts that officers enter; participation records. Plus the roster fields above, kept for the workspace.
- **Where the data comes from.** The end-of-day daily read (D72, issue #294) moves the daily read from the morning to the end of the server day, before the server resets. It costs no extra API calls: the same 1 + k calls (D60) read the rosters whole. `daily_rosters` has no `raw_json` (D60), so no donation history exists before it. Event snapshots keep storing these fields in `raw_json` as before.
- **Open for the owner: retention.** This decision sets no retention rule for Discord ids, display names, officer-entered facts, participation records or the roster fields. D2 keeps public stats forever; whether personal data follows the same rule, and who can delete a person's record, is not decided.
