## D71 — A private workspace per alliance: Discord sign-in, every roster field for its own leadership (2026-11-16, owner, 11a, issue #303)

Why: the owner wants a private area where an alliance's leadership sees everything the game API returns about its own members, not only the public stats. Owner answers (2026-11-16): sign in with the Discord account and the alliance's leadership role; "capture everything and show everything possible", to that alliance's leadership only; no extra API calls. The owner also asked how this works for other alliances; see "Other alliances". Issues: umbrella #293; this decision #303; end-of-day read #294; sign-in #295.

- **Name.** The private area is a **workspace** (glossary). "Leadership" already means the R5 and R4 roles in `lib/queries/leadership.ts`.
- **Who: sign-in.** Discord OAuth with scopes `identify guilds.members.read`. After the code exchange the server calls `GET /users/@me/guilds/{guild_id}/member` with the member's token. Access is granted when the member's role ids intersect the workspace's `leader_role_ids`, or when the Discord user id is on the workspace's allowlist. No bot joins the Discord server. No new dependency: two `fetch` calls, `node:crypto` and `secretEquals` (`lib/auth.ts`). `DISCORD_CLIENT_ID` and `DISCORD_CLIENT_SECRET` are optional, so the app starts without them; the secret joins the log redaction list. The Discord server id and the role ids live in the database, so a new alliance needs no deploy.
- **Who: sessions.** The cookie (`__Host-` prefix) holds a random 32-byte token: HttpOnly, Secure, SameSite=Lax (the OAuth callback arrives cross-site). A session lasts at most 24 hours and belongs to one workspace; a session of one workspace is refused under another slug. After 24 hours a silent Discord re-authorisation (`prompt=none`, no token stored) checks the role again, so an officer whose role was removed loses access within a day. The database stores only the token's sha256 (`workspace_sessions`), so access can be revoked at once; `/admin` gets a "sign out everyone in this workspace" control. Allowlist rows record who added them and an expiry date. Discord two-step verification is not required (owner, 2026-11-16). The OAuth `state` is in a separate 10-minute cookie, compared in constant time. Writes go through route handlers only and require Origin equal to the app origin (`Sec-Fetch-Site: same-origin` when the browser sends it), a JSON content type and a valid session; the rate limits reuse `auth_attempts`. `/admin` and its PIN (D3) are unchanged.
- **Who: tenancy.** Every private table has `workspace_id NOT NULL`. Private queries take a branded `WorkspaceAccess` value that only `requireWorkspace(slug)` creates, and the workspace id never comes from a request. Shared tables that hold roster data (`daily_rosters`, `alliance_snapshots`, `member_snapshots`) are read by `lib/private` only for rows whose alliance is the workspace's own (`union_id = access.unionId`), so a player who moves to another alliance is visible to the old one only up to the move. A two-tenant PGlite test must show that one workspace cannot read another's rows, including a player who moved from one alliance to the other.
- **Who: the fence, both ways.** Private code lives in top-level `lib/private/`, not in `lib/queries/private/`: `lib/queries/blocked-keys.test.ts` scans `lib/queries` non-recursively, so a subfolder would escape it. An `import-x/no-restricted-paths` zone forbids importing `lib/private` from `app/(pages)`, `app/_ui`, `app/api`, `lib/queries`, `lib/notify*`, `lib/discord-*`, `lib/logger.ts` and `lib/run.ts`. A second zone forbids `lib/private` from importing `lib/notify*` and `lib/discord-*`; it logs only through a wrapper that takes a code and numbers. A test asserts that the roster fields above are read only in `lib/repo` and `lib/private`. Private pages and handlers sit under `app/(private)/w/[slug]` and `app/(private)/api/w/[slug]`; the URL is `/w/[slug]`. Their responses carry `Cache-Control: private, no-store`, and their metadata is static: no query runs before the access check, so a link pasted in Discord previews nothing.
- **Leadership only** (owner, 2026-11-16). Only the alliance's leadership uses and edits the workspace. That includes the notices library: event notices, rules and strategies, sometimes with images, which the leadership posts today on the in-game notice board, in in-game mail and on Discord.
- **One level of access** (owner, 2026-11-16). Every leadership member (R5 and R4) can view and edit everything in their alliance's workspace. There are no per-person permissions inside a workspace.
- **Regular members are out of scope** (owner, 2026-11-16). Anything for non-leadership members needs its own decision later; the owner says it "has to be thought through carefully". Issue #301, the member self-report link, is deferred on that basis.
- **Other alliances.** The owner registers a workspace on `/admin` (PIN): the union id (it must be in `ALLIANCES`), the Discord server id, the leadership role ids and a slug. No deploy. Later, self-service (issue #302): the alliance's R5 proves ownership by putting a one-time code in the in-game alliance declaration, which `/v1/alliances/{id}` returns as `declaration`. Until then only the owner registers one.
- **What it shows.** Every roster field the API returns for the alliance's own members, when the API returns it: `daily_tech`, `daily_honor`, `active`, `joined_at`, `online`, `last_online_at`, `x`, `y`. Only that alliance's workspace sees them, only its signed-in leadership. `daily_tech` is "tech points donated today" and `active` is "weekly activity" in the API docs. A null `daily_tech` is shown as unknown, never as 0. On 2026-11-16 the API returned `joined_at` and `last_online_at` as null for every member and `online` was never true in any stored read; the join date therefore comes from member history ("seen since", D60) and online status stays hidden while the API leaves it empty. Copies and exports (for example "copy for a spreadsheet") leave out `x`, `y`, `online` and `last_online_at`. The photo still reaches pages only as the image `/img/avatar/[uid]` serves (D22); `avatar_url` is never returned.
- **Languages** (owner, 2026-11-16). The leadership of OGs has people who read only English, only Portuguese or only French; today they use a Discord translation bot and the game's translations. The workspace is therefore not English-only: D48's rule that `/admin` stays English does not apply to it. Its screens use a workspace dictionary of their own (`en`, `pt-BR`, `fr`), separate from `lib/copy.ts`, so the public i18n check and the public pages' payload do not change. Text that officers write (notices, notes) has a Translate action: player names are replaced by placeholders before sending, the game-term glossary goes with the request, numbers and dates stay as written, and the result is cached for the next reader of that language. The original stays one tap away.
- **Open for the owner: the translation service.** It is decided together with the screenshot import (issue #299, an external processor through the AI Gateway). This decision picks none.
- **What stays as it is.** Public pages, public routes, Discord messages, `run_logs` and `app_errors` are unchanged. `BLOCKED_ROSTER_KEYS` (`lib/queries/blocked-keys.ts`) is unchanged and still binds `lib/queries`, every route, page, log and message outside `lib/private`. The hard rule in CLAUDE.md now allows `lib/private/` code to return those fields to its own alliance's workspace.
- **Supersedes.** Plan §12.6, "No user accounts, no OAuth", for the workspace only; the rest of the site has no accounts. It is the story §12.6 said §12.2 would need when the alliance stores anything private (Discord ids). It also changes §12.1: the blocked fields are served to the workspace.
- **New stored data.** Discord user ids and display names of the people who sign in (and their session hashes); member facts that officers enter; participation records. Plus the roster fields above, kept for the workspace.
- **Where the data comes from.** The end-of-day daily read (D72, issue #294) moves the daily read from the morning to the end of the server day, before the server resets, and keeps each roster whole for all 20 tracked alliances (owner, 2026-11-16), so an alliance that joins later already has its history. A roster of one alliance is never shown to another. On a normal day it costs no extra API calls: the same 1 + k calls (D60) read the rosters whole. `daily_rosters` has no `raw_json` before D72, so no donation history exists before it. Event snapshots keep storing these fields in `raw_json` as before.
- **Open for the owner: retention.** This decision sets no retention rule for Discord ids, display names, officer-entered facts, participation records or the roster fields. D2 keeps public stats forever; whether personal data follows the same rule, and who can delete a person's record, is not decided. It must be decided before officer notes are imported from the spreadsheets (issue #297) or sent for translation.
