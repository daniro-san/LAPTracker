## D86 — The server fight clock and the compare page's server pulse: one notion of "sampled", unsampled events disabled (2026-11-16, owner, 08zzzzn, issue #284)

Why: samples (D69) exist from release v5.7.0; the first sampled KvK is Saturday 2026-11-21. Every earlier event has none and none can be rebuilt. The owner (2026-11-16): events without samples cannot be compared with other events in the sample-based views; they appear disabled, with the reason in plain words, and the views light up by themselves once samples exist, with no further code change. This is build 1 of #284: the cross-event views. The window picker and the officer-only views are later builds.

- **One notion of "sampled".** `sampledEventIds(db, ids?)` (`lib/queries/fight-clock.ts`): a public event with at least one snapshot of `phase = 'sample'` that is not running and holds an alliance row that was read (no error) and is fresh. It is its own small query, not a `samples` count on `listEvents`: `listEvents` runs on every page (the header's event list), and only these views need the answer, so a count there would add a query to every page view. Every view reads sampled-ness from this one function; nothing infers it from an empty slot list.
- **The read model** (`eventPulses`, `getFightClock`; pure arithmetic in `lib/fight-clock.ts`). Per event: its slots on the server clock, each with the kills gained by all tracked alliances in it, its share of the kills the event gained over its slots, and its state (`moved`, `still` = no update from the game, `missing`); the event's busiest rolling 30 minutes (the best two slots in a row, `busiestSpan`, named once 4 slots are compared, as on the event page). The slots are `serverPulse`'s intervals (the Start, then each sample): consecutive and one cadence long, so the last ends on the last sample's slot and each earlier one a cadence before the next. The first one is the slot that holds the Start (12:00 for the interval 12:01 to 12:15). A slot carries its start on the grid and `minute`, its start in minutes on the server clock counted from the server midnight of the first slot (it keeps counting past 1440 for an event that runs past midnight): two events line up on `minute`, so noon is noon in both whatever the viewer's zone (D38); the labels use the viewer's clock. A loss of kills (a member left) counts 0 in a slot, so it never shrinks the total the shares divide by. The shares of the `moved` slots sum to 1 when the event gained kills.
- **Reads.** `progressRows` through the event cache (D79): the `progress-done` key (a day) once the event's End has a row, `progress` (a minute) while it has none. `RowsOf` is injected, as the event page's turnout loader is, so `lib/queries` does not import `next/cache`; `app/_ui/event-page.ts` supplies `progressRowsOf`, which `loadProgress` now uses too, so the event page and these views share one cache entry per event. A finished event costs nothing after the first view. Events are read one after the other, so a cold cache holds one connection at a time (each cached read opens its own). Only alliance totals are read, never rosters, names or blocked roster keys. The sampled-ness query runs per view (not cached): one distinct select over snapshots with an `exists` on alliance rows.
- **Unsampled events** come back in the same list, `sampled: false`, `clock: null`, and cost no row read. Why an unsampled event is off (`offReason`, from data and `now`, never a hard-coded date): `since` (it is older than the first sampled event: "they start with the event of Nov 21", the date of the first sampled event), `next` (no event is sampled yet: "they start with the next event"), `waiting` (it has no End row and its time is less than a day ago or ahead: the readings come in while it runs) and `missed` (it came after sampling began and has none).
- **Fight clock page** `/events/fight-clock` (public). Rows: scheduled public events (a manual round has no schedule), newest first. Columns: the slots on the server clock, shared by every row, so a column is one time of day. A box's height is the slot's share of that event's kills, scaled against the tallest share on the page; a hollow dashed stub is "No update from the game"; a hairline is "No reading"; the busiest 30 minutes are outlined (plum border round the pair) and named in a sentence per row; the hours are HTML labels under the strip; every figure is in the row's Details table (share, kills gained). A row links to `/events/<id>#live-during`. An unsampled event is a muted dashed card, not a link, with the reason. With no sampled event at all the page shows the disabled rows and one sentence: "Each event's 15-minute readings will be drawn here, starting with the next event." Placement: a first item in the header's Events list (the site's events navigation, on every page) and a link under the pulse in the event page's "During the event" section. 16 columns at 360 px are 20 px each with a 2 px gap; a window of more than 24 slots would pass the 14 px floor, so it needs the window picker.
- **Compare page.** A "Server pulse" section after the totals (the list view only, not one alliance or a player): events A and B lined up on the server clock over the union of their slots, each event's busiest 30 minutes in a sentence, one Details table with both. When either event is unsampled the section is a muted frame with the reason ("Event A has no 15-minute readings, so the two events' pulses cannot be compared"; B; neither) and nothing is drawn. `bothCover(a, b)` (the server-clock minutes both events have a slot for) and each event's slot list are what the window picker (From and To, shortcuts) will call; the picker is not built.
- **The last quarter hour.** Like the event page, the slots end at the last sample: the End's alliance rows are not read (`progressRows`), so the interval from the last sample (15:45) to the End (16:00) is not drawn.
- **Not done.** The window picker; the officer-only views (our kills against our might per slot, members by slot) from a per-alliance-per-slot aggregation. `readingsOf(rows)` (`lib/queries/live.ts`, the Start and the samples as readings) is the shared first step they would use next to `serverPulse`.
- **Seed.** `scripts/seed-samples.ts` samples the second seed event as well (a different shape, fighting 13:00 to 13:45Z), so locally two events are sampled and the oldest is a disabled row.
- **Amended 2026-11-16 (review of PR #343).** The fight clock shows the newest `FIGHT_CLOCK_EVENTS` = 12 scheduled events (about three months), so its cold reads and its page stay bounded as events accumulate. Tapping a cell to open that range (issue 284) is not built: it comes with the window picker, which owns the range; until then a row links to the event's "During the event" section.
- **Amendment 2026-11-17 (owner delegated; persona panel + adversarial review).** (1) The "since" reason names the first sampled event over all scheduled public events, not the oldest sampled one among the 12 shown; otherwise, once the window slides, an older unsampled event would name a later date. (2) "Missed" reads "No usable {min}-minute readings were stored for this event.": readings can be taken but stale or failed. (3) The lead says what is counted and that the last quarter hour before the End is not drawn: "The tracked alliances' kills, {min} minutes at a time, event by event. A box's height is its share of the kills drawn for that event, from the Start to its last reading." The four disabled reasons and the compare page's reasons are unchanged.
- **Amended 2026-11-21 (issue 473).** The header's Events list shows the fight clock link only once some public event has a usable 15-minute reading (`sampledEventIds`); before that the page has only "off" rows. The shared event list (`events`, D143) carries `sampled` per event; a sample's run invalidates it. The fight clock page itself and the live section's link are unchanged.
