## D148 — Browser notifications for officers: Web Push on node:crypto, one device at a time, four uses, counts and a link only (2026-11-21, owner, issue 558; amends D71, D137, D141)

Why: officers learn about the Raid Shield check, a failed night read, a member's "This is me" and a roll call only when they open the desk. The owner (issue 558, scope confirmed 2026-11-21) wants a browser notification for each, all four built together, opt-in per person and per use.

**The protocol, with no dependency** (`lib/web-push.ts`). Web Push (RFC 8030) with VAPID (RFC 8292) and aes128gcm payload encryption (RFC 8291, RFC 8188), on `node:crypto` only: ECDH P-256, HKDF-SHA-256, AES-128-GCM and an ES256 JWT (`ieee-p1363` signatures). The `web-push` package is not used: the platform does all of it in about 150 lines, and RFC 8291's own test vector checks the encryption (`lib/web-push.test.ts`).

- One POST per device: `TTL` 12 hours (a phone that is off gets it when it wakes the same day), `Urgency: normal`, one record of 4096 octets, a VAPID JWT for the push service's origin that expires after 12 hours.
- **A 5-second timeout** (`SEND_TIMEOUT_MS`). A send never throws: 201/202 is `ok`, 404 or 410 is `gone`, anything else, a timeout or a redirect included (redirects are refused, so a push never leaves the allowed hosts), is `failed`. The endpoint is hashed as parsed (`new URL(…).href`), so one device never gets two rows.
- **Only the browsers' push services** (`PUSH_HOSTS`): `fcm.googleapis.com`, `android.googleapis.com`, `push.services.mozilla.com`, `notify.windows.com`, `push.apple.com`, each with its subdomains, over https on the default port. Any other endpoint is refused when it is saved (400), so the server never posts to another host.

**The site's keys** (`lib/env.ts`, all optional, server only): `VAPID_PUBLIC_KEY` (the 65-byte public point, base64url), `VAPID_PRIVATE_KEY` (the 32-byte private scalar, base64url, a secret, added to `secretsOf` so logs mask it) and `VAPID_SUBJECT` (`mailto:` or `https:`, the contact push services may write to). The subscriptions are sealed under `WORKSPACE_KEYS_SECRET`. **Without all four, the feature does not exist**: no Notifications card, the route answers `403 turned_off`, and no notification code reads the database or sends (`pushConfig`). `pnpm push:keys` prints a fresh pair (`scripts/push-keys.ts`); it writes nothing. Replacing the pair later stops every device until its officer taps "Enable on this device" again (the browser's subscription is bound to the old key; the card drops it and subscribes again).

**Storage** (`lib/schema-push.ts`, migration `0065_push_subscriptions`, `pnpm db:generate`):

- `push_subscriptions`: one row per officer and device in a workspace. The subscription's JSON (endpoint and keys) is sealed with AES-256-GCM as D129's webhooks are, under `laptracker/push-subscription/<workspace id>` as associated data, and opened only in `lib/push.ts` at send time. The row keeps the endpoint's sha256 (to find this device's row without opening any), the uses it is on for, the desk's language on the device when it was saved (the notifications' language), when it was saved and the push service's last 201. Unique per workspace and endpoint: another officer turning notifications on in the same browser takes the row over. At most 10 devices per officer per workspace; the oldest goes.
- `push_marks`: per workspace, each trigger's last value notified (`shield:<day>`, `night:<day>`, `claim:<user>`, `rc:<entry>:<week>`). A trigger notifies only for the one caller whose upsert stores a new value (INVARIANT `push.once-per-trigger`), so two ticks never send the same notification twice.
- Both are in `WORKSPACE_TABLES` (D125): deleted with the workspace, never downloaded.

**Officers only** (INVARIANT `push.officers-only`, `pushRecipients`). A device is notified only while its person is not blocked and holds an officer's session of that workspace that has not ended (at most 7 days after sign-in, D71, D99). A member's session, another workspace's session or an ended one never counts, so an officer who stops opening the desk stops getting notifications within a week, and opening it again brings them back (the card says so). Devices are deleted:

- when the push service answers 404 or 410 for one, or this master key cannot open it;
- on "Turn off on this device", and on Sign out on the device: the sign-out sends this browser's endpoint and the server deletes that person's row for it (the browser's subscription is ended too);
- when a sign-in through Discord refuses the person (they left the server, lost the role, were blocked or their allowlist entry ended), or lets them in as a member only: all their devices in that workspace.

**The four uses.** Each has its own switch on the card, and each follows its D134 switch where it has one: the use is not offered, and nothing is sent, while the feature is off. A notification shows on lock screens, so it holds **counts and a link only**: never a member's name, uid or any private field (the test decrypts what reached the device and checks). The words are in `lib/copy-push.ts`, in the device's desk language (EN, PT-BR, FR).

**When a roll call opens and closes** (an assumption the owner can change; the desk has no such notion). A Calendar roll call is open for 24 hours around its activity's time A (its day and time, server time): **Raid prep** (the KvK shield, answered before KvK) from A − 24 h until A; the others (Undead Siege, Cheese Trap, Elixir Scramble teams: who took part) from A until A + 24 h. The "open" reminder is due in its first 3 hours when anyone is not set, the "left" one in its last 3 hours (about a day later) while anyone still is. The desk has no closing time; this only sets when the reminders come. The counts are the Roll call page's own (`weekItems`): away members left out, a team only its members. Roll calls added by hand are not reminded.

**No new cron and no extra wake of the database** (amends D141). The roll call reminders and the night read's notification run after the tick's answer (`lib/push-tick.ts`, `after`), on ticks that open the database anyway. The tick opens it at least once every 3 hours (D141's heartbeat), so each 3-hour reminder window gets a tick; a reminder comes up to 3 hours after its moment, never twice. The Raid Shield notification runs inside the shield tick's own `after` (lib/shield-tick.ts). Every send is after the answer or the read, has the 5-second timeout, and its failure is one code-only log line (`push.failed`): it never fails the user's action or the read. The log line of a send is counts only (`push.sent`: use, sent, gone, failed).

**One exception to D71's fence.** `lib/push-tick.ts` may import `lib/private/push-roll-calls.ts`, and only that module (`eslint.config.mjs`), so the reminder and the Roll call page count alike. That module builds a `WorkspaceAccess` with `officerAccess` for one of the workspace's own officers whose device is on for roll calls, reads only that workspace's own alliance, and returns counts, the roll call's kind and team, and its address.

**The card** (Alliance settings → Notifications, `app/(private)/_ui/PushSettings.tsx`, EN · PT-BR · FR; only with the site's keys). Each officer turns it on for their own device:

- The device's state ("On for this device." / "Off for this device.", announced) and its one button come first, then "Notify this device about:" and one switch per offered use, with a line on what it sends. The night read's switch starts off. "Enable on this device" asks the browser's permission only on that tap (iPhone requires it inside the tap), registers the service worker and saves the subscription with the switches as they are. Once on, a switch saves at once (the switches wait while it saves), and "Turn off on this device" ends it on the server and in the browser.
- It says the notifications hold counts only; how iPhone and iPad take them ("open the desk in Safari, tap Share (or ••• → Share), then Add to Home Screen. Open the desk from that icon, then open Alliance settings → Notifications."); that the Home Screen icon may ask for a Discord sign-in once more (it keeps its own); how Android does; and "A sign-in lasts 7 days; after that, sign in again and they come back."
- Safari on an iPhone or iPad outside the Home Screen app reads "On iPhone and iPad, notifications work only when the desk is opened from its Home Screen icon (see below)."; another browser without push reads "This browser can’t show notifications from the desk."; a blocked permission reads how to allow it again.
- The desk's language switch on a device also moves that device's notifications to the new language.
- **Home** shows a one-time line to officers, while the site has push keys and the device has no notifications on: "Get notifications on this phone · Alliance settings →", with Hide (kept in the browser's storage, a convenience).

**The service worker** (`public/sw.js`, scope `/w/<slug>/`, registered from the card). It shows a push as a notification (title, body, tag, the desk icon) and, on a tap, focuses a window already on that page or opens it. Only a `/w/…` path of this site is opened. It caches nothing and has no `fetch` handler. The page CSP gains `worker-src 'self'` (proxy.ts): without it the worker falls back to `script-src`, where `'strict-dynamic'` drops `'self'`.

**Route** `POST /api/w/[slug]/push` (officers only, same origin, JSON, `401 signed_out`): `subscribe` (the subscription, the uses, the language), `uses` (by endpoint), `unsubscribe` (by endpoint), `language` (by endpoint: the desk's language switch on that device). Only the signed-in officer's own rows are written: `uses` or `language` on a device of another officer or workspace answers `404 not_found`, `unsubscribe` answers 200 (it deletes only the officer's own row, so nothing changes). 30 writes per 15 minutes per officer (`auth_attempts`). Counted as `ws_action` `push` / `add`, `save`, `delete`. `POST /api/w/[slug]/logout` takes an optional `endpoint`.

**Analytics.** `ws_push_enabled` and `ws_push_disabled` with `{use}` (one event per use turned on or off; turning a device on or off counts each use it has), and `ws_action` `push`. Never the endpoint or the device.

**Owner steps.**

1. In a terminal in the repository: `pnpm push:keys`. It prints `VAPID_PUBLIC_KEY=…`, `VAPID_PRIVATE_KEY=…` and a `VAPID_SUBJECT` line to fill.
2. In Vercel → the project → Settings → Environment Variables, add for Production (and Preview if wanted): `VAPID_PUBLIC_KEY`, `VAPID_PRIVATE_KEY` (tick "Sensitive") and `VAPID_SUBJECT` (`mailto:` and an address you read). `WORKSPACE_KEYS_SECRET` is already set.
3. Redeploy. Alliance settings then shows the Notifications card. Do not paste the private key anywhere else, and keep the same pair: a new pair needs every officer to enable again.
4. On a real iPhone: add the desk to the Home Screen, open it from the icon, sign in if asked, enable on this device, and check that one notification arrives. The build was checked in desktop Chrome with a stubbed push service only.

**Not built here.**

- `pushsubscriptionchange` (a browser renewing a subscription by itself): the old row is deleted on its first 404/410, and the card shows "Off" until the officer enables again.
- Cleaning old `push_marks` rows: a few per workspace and week.
- A reminder before notifications pause (the sign-in ending): a follow-up.
- The officers-only rule counts a session that has not ended (7 days), not D99's 24-hour role check, so a person who loses the role in Discord and never signs in again gets counts for up to 7 days. The owner may ask for a shorter bound (`checked_at` within N hours).
- Notifications for members: never (D75, D71: nothing about a member reaches other members).
