## D72 — The daily read runs at the end of the server day and keeps every roster field (2026-11-16, owner, 11b, issue #294)

Why: `daily_tech` ("tech points donated today", API docs) is a counter of the server day. The 06:00 read (D60) saw about 6 of its 24 hours, and `daily_rosters` stored no `raw_json`, so no donation history existed. The owner chose no extra read: move the daily read to the end of the server day, before the reset, and keep every field. This supersedes D60's `06:00` default and its skip on a scheduled event's day. D60 and D67 are otherwise unchanged.

- **When.** `DAILY_ROSTER_AT` defaults to `23:45` server time. The tick comes at minutes 7, 22, 37 and 52 (D26), so the 23:52 tick, the last of the server day, runs the read. The read takes about 10 s and is cut at 100 s (D25), so it ends by 23:53:40.
  - Owner facts (2026-11-16): the game's daily donation counter resets at exactly 00:00 server time (UTC−2), so a read at 23:52 sees 23 h 52 min of the day. Vercel production has no `DAILY_ROSTER_AT` variable, so the new default applies on deploy.
  - Why 23:45 and not 23:30: with 23:30 the 23:37 tick would read and the last 23 minutes of donations would be lost every day. 23:45 gives one tick per day. A missed or dropped 23:52 tick (D26) leaves that day with no read: a gap, as D60 already says for a missed window.
- **Never after midnight** (INVARIANT `daily-read.ends-before-midnight`).
  - `dailyReadDue` looks only at today's `DAILY_ROSTER_AT` (server date). A tick at 00:07 is on the next server day, and that day's 23:45 is ahead, so it reads nothing. The window `[23:45, + SNAPSHOT_WINDOW_MIN)` therefore ends at 00:00 in practice. A tick after midnight never runs the day before late.
  - The tick does not start the read when `now + RUN_DEADLINE_MS` (100 s) is past the end of the server day, i.e. after 23:58:20. A late tick would otherwise read rosters after the 00:00 reset and store them under the day before.
- **Quota.** 23:52 server time is 01:52 UTC on the next UTC day. So Friday's read is spent from Saturday's UTC count (21 calls), next to the Saturday Before and After (42). The rule is unchanged and still holds: the read starts only when `remaining ≥ requiredQuota(k) + requiredQuota(20)` (100 for 20 alliances, INVARIANT `budget.daily-keeps-event-reserve`), so the Saturday snapshots keep their reserve. Saturday's own read is at Sunday 01:52 UTC. The Friday check (Friday 20:00 server = 22:00 UTC) sees the same spend as before: one daily read (Thursday's, at Friday 01:52 UTC) and the rehearsal.
- **Event days too.** The skip (D60, INVARIANT `daily-read.not-on-event-day`) is removed, and `hasScheduledEvent` with it. The event's Before (10:00) and After (14:00) read the rosters hours before the day ends, so they do not carry the day's counters, and at 23:52 nothing collides with the event's phases (their windows end by 14:45). Without this, every Saturday would have no end-of-day counters. On an event day the member history now has three rosters: Before, After and the daily read.
- **One action per tick.** If a phase, the Friday check or a rehearsal slot is due at 23:52, it takes the tick and the day has no read. With the documented settings nothing is due then; an owner who moves `REHEARSAL_AT`, `SNAPSHOT_AFTER` or `QUOTA_CHECK_AT` near 23:45 would cause it.
- **Every roster field.** `daily_rosters.raw_json` (jsonb, nullable, migration 0017) stores `trimRaw(raw)` (`lib/raw-json.ts`, plan §6) for each roster read, as event snapshots do: every member field, `daily_tech`, `daily_honor` and `active` among them. Error rows have none, and rows from before this change have none. A D67 retry replaces the day's roster and its `raw_json` together (one upsert).
- **Privacy.** `raw_json` is never selected by a read model, route, page, log or message (CLAUDE.md hard rule; `BLOCKED_ROSTER_KEYS` unchanged). Every select from `daily_rosters` lists its columns (`lib/queries/daily-runs.ts`, `lib/queries/history-readings.ts`, `lib/queries/member-history.ts`, `lib/repo/daily-reads.ts`). Who may later read these fields, and where, is decided separately (D71).
- **Size, measured** (local Postgres, fixtures `v1-20261116T105019Z` and `v1-ids`): OGs (101 members) `pg_column_size(raw_json)` = 9,305 bytes per day (38,885 bytes as text; Postgres compresses it). 19 rosters: average 8,309 bytes, largest 10,076. For 20 alliances a year: 20 × 8,309 × 365 ≈ 61 MB (≈ 68 MB at OGs' size), on top of D60's member arrays (≈ 2.7 KB per roster, ≈ 20 MB a year).
- **A read that falls short has minutes, not hours.** The admin line arrives at about 23:52. A D67 Retry works only for today's server day, so it must be pressed and finish before 00:00: about 6 minutes, and a Retry started after 23:58:20 can itself run past the reset (the retry route has no such guard). At 00:00 `/admin` shows the new day and the Retry card is gone; the day that fell short keeps its gap. Not built: an automatic retry, and a midnight guard on the retry route (handoff 11b, Open issues).
