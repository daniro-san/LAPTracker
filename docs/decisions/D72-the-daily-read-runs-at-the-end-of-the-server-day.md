## D72 — The daily read runs at the end of the server day and keeps every roster field (2026-11-16, owner, 11b, issue #294)

Why: `daily_tech` ("tech points donated today", API docs) is a counter of the server day. The 06:00 read (D60) saw about 6 of its 24 hours, and `daily_rosters` stored no `raw_json`, so no donation history existed. The owner chose no extra read on a normal day: read near the end of the server day, before the reset, and keep every field. This supersedes D60's `06:00` default and its skip on a scheduled event's day. D60 and D67 are otherwise unchanged.

- **When** (owner, 2026-11-16). `DAILY_ROSTER_AT` defaults to `23:30` server time. The tick comes at minutes 7, 22, 37 and 52 (D26), so the 23:37 tick runs the read; it sees 23 h 37 min of the day. The 23:52 tick may retry what fell short (below). Accepted cost: donations made between 23:37 and 00:00 are not captured.
  - Owner facts (2026-11-16): the game's daily donation counter resets at exactly 00:00 server time (UTC−2). Vercel production has no `DAILY_ROSTER_AT` variable, so the new default applies on deploy.
  - Both ticks must fall in the window `[DAILY_ROSTER_AT, + SNAPSHOT_WINDOW_MIN)`: with 23:30 that needs `SNAPSHOT_WINDOW_MIN` ≥ 23 (it is 45).
- **The automatic retry at 23:52** (owner, 2026-11-16). On a later tick of the same server day, inside the window, when today's read is `failed` or `partial`:
  - it reads again only the alliances with no roster for the day (error rows and alliances never reached), D62's idea for snapshots;
  - the quota check comes first, with the same rule as the read, sized to those alliances;
  - each roster read is stored with D67's upsert, and the day's outcome is judged on every alliance, as D67 does;
  - a roster it kept is judged fresh against the start of the read it completes (the 23:37 `started_at`, read before its claim moves it), not against its own start: a roster 6–20 minutes old at 23:37 is not made stale by the 15 minutes between the ticks (review of #314). D67's Retry, which reads every roster again, judges kept rosters against its own start as before;
  - a day with a roster of every alliance (a `complete` day included) is never read again automatically;
  - at most once per day: `daily_reads.auto_retry_at` is set by the claim, a conditional update, so a third tick cannot loop. The claim also needs the read to have started at least 10 minutes earlier, so a second pinger in the 23:37 minute (D43) is not taken for the 23:52 tick;
  - it writes `daily.auto-retry` (with the number of alliances) where a read writes `daily.start`, and moves `started_at`, so `/admin/runs/daily/[day]` shows its calls as the latest attempt; `calls_used` stays the day's total.
  - Cost: nothing on a normal day (one read, 21 calls). On a bad day, 1 quota call plus one per alliance without a roster (retries of a 502/503/504 included).
  - A roster that was read but is stale is not read again automatically: it is a roster, not a failure (D62). Such a day stays `partial` and can be retried by hand.
  - If the admin presses Retry (D67) less than 10 minutes before the 23:52 tick, that tick does not retry automatically.
- **Never after midnight** (INVARIANT `daily-read.ends-before-midnight`).
  - `dailyReadDue` looks only at today's `DAILY_ROSTER_AT` (server date). A tick at 00:07 is on the next server day, whose 23:30 is ahead, so it reads nothing. The window therefore ends at 00:00 in practice: a tick after midnight never runs the day before late.
  - One pure function, `endsInServerDay(now, RUN_DEADLINE_MS, cfg)` (`lib/schedule.ts`), decides whether a read that may last 100 s (D25) ends inside the server day. The tick's read and its automatic retry, and `/admin`'s Retry, start only when it holds, so none starts after 23:58:20. Otherwise rosters read after the 00:00 reset would be stored under the day before.
  - `dailyReadEndsInDay(now, cfg)` (`lib/daily-read.ts`) is that function with `RUN_DEADLINE_MS` bound. `retryDailyRead` applies it and returns `"too-late"`; `POST /api/daily-read/retry` maps that to 409 `daily_read_too_late`: "Too close to the server reset (00:00). This day keeps its gap." `/admin` calls it to hide the Retry card in those last 100 s. Neither app file imports `RUN_DEADLINE_MS` (review of #314).
  - `RUN_DEADLINE_MS` moved from `lib/collector.ts` to `lib/compute.ts` (pure), so code outside the collector can read it; `lib/collector.ts` re-exports it.
- **What is left.** If both the 23:37 and the 23:52 ticks are lost, or both reads fall short and nobody retries before 23:58:20, the day keeps its gap. A past day is never read again (D67).
- **Quota.** 23:37 server time is 01:37 UTC on the next UTC day. So Friday's read is spent from Saturday's UTC count (21 calls, more on a bad day), next to the Saturday Before and After (42). The rule still holds: a read or automatic retry of k alliances starts only when `remaining ≥ requiredQuota(k) + requiredQuota(20)` (INVARIANT `budget.daily-keeps-event-reserve`). The Saturday snapshots keep their reserve. Saturday's own read is at Sunday 01:37 UTC. The Friday check (Friday 20:00 server = 22:00 UTC) sees the same spend as before: one daily read (Thursday's, at Friday 01:37 UTC) and the rehearsal.
- **Event days too.** The skip (D60, INVARIANT `daily-read.not-on-event-day`) is removed, and `hasScheduledEvent` with it. The event's Before (10:00) and After (14:00) read the rosters hours before the day ends, so they do not carry the day's counters. At 23:37 and 23:52 nothing collides with the event's phases, whose windows end by 14:45. Without this, every Saturday would have no end-of-day counters. On an event day the member history has three rosters: Before, After and the daily read.
- **One action per tick.** If a phase, the Friday check or a rehearsal slot is due at 23:37 or 23:52, it takes that tick. With the documented settings nothing is due then.
- **Every roster field, for every tracked alliance** (owner, 2026-11-16: all 20). `daily_rosters.raw_json` (jsonb, nullable, migration 0017) stores `trimRaw(raw)` (`lib/raw-json.ts`, plan §6) for each roster read, as event snapshots do. That includes every member field, `daily_tech`, `daily_honor` and `active` among them. It is stored for every alliance in `DAILY_ROSTER_IDS` (all 20 by default). Error rows have none, and rows from before this change have none. A retry (D67's or the automatic one) replaces the day's roster and its `raw_json` together (one upsert).
- **Privacy.** `raw_json` is never selected by a read model, route, page, log or message (CLAUDE.md hard rule; `BLOCKED_ROSTER_KEYS` unchanged), and one alliance's fields are never shown to another alliance. Every select from `daily_rosters` lists its columns (`lib/queries/daily-runs.ts`, `lib/queries/history-readings.ts`, `lib/queries/member-history.ts`, `lib/repo/daily-reads.ts`). Who may later read these fields, and where, is decided separately (D71).
- **Size, measured** (local Postgres, fixtures `v1-20261116T105019Z` and `v1-ids`):
  - OGs (101 members): `pg_column_size(raw_json)` = 9,305 bytes per day (38,885 bytes as text; Postgres compresses it).
  - 19 rosters: average 8,309 bytes, largest 10,076.
  - For 20 alliances a year: 20 × 8,309 × 365 ≈ 61 MB (≈ 68 MB at OGs' size), on top of D60's member arrays (≈ 2.7 KB per roster, ≈ 20 MB a year).

**Amendment (2026-11-20, D133, issue 459).** The ranks board is read right before the day's read, in its window. A workspace's alliance outside the top 20 is read on its own key when it saved one. `daily_rosters.read_day` no longer references `daily_reads`, because a lookup's roster may come before the day's read. The storage estimate above is for 20 alliances: each workspace outside them and each lookup add about 8 KB a day.
