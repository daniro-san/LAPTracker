## D5 — Data sources: /v1 is the product; the internal API is optional garnish (2026-11-04, plan §3.5)

The documented `GET /v1/alliances/{id}` is the only required source; it refreshes on read. The site's internal API is used read-only for the ranks board (cross-check, 0 quota) and as a per-alliance fallback that accepts only `live: true` rosters, recorded as `source = internal`. The site's refresh endpoint is closed to outsiders on purpose; we never call it or imitate the site's headers. No number in a delta depends on an undocumented endpoint. One API key, no pooling.

**Widened (2026-11-20, D133, issue 459; owner's decision of 2026-11-19).** The ranks board is no longer only a cross-check: it also picks the day's tracked set, and its might, kills and places are shown on `/alliances` and each alliance's page, labelled "Ranks board". Board numbers still never enter a delta. The endpoint, GET only, with no refresh call and no Origin, Referer or cookies, is unchanged.

**Cross-reference (2026-11-21, D69 amendment "wrong-alliance reads").** A `/v1` 200 that holds another alliance's roster counts as a `/v1` failure. In a Before or an After it gets the same one internal fallback read, which is checked the same way. No new use of the internal API.

**Amendment 2026-11-28 (owner, 2026-11-28, issue 789: "a sondagem, faz uma chamada em prod ai, nao vou trazer a chave pro meu arquivo local"): a one-off /v1 discovery read from production, 12 calls.** To find fields and endpoints the API docs do not mention, the production tick that falls in 02:30–02:45 ST on Sun 2026-11-29 (04:30 UTC) sends one GET to each of 12 paths on the `/v1` base URL, in order, on LAP_API_KEY, with the adapter's usual headers (key, User-Agent, Accept; no Origin, Referer or cookies), paced 500 ms apart, with no retry (`lib/api-probe.ts`, `probePath` in `lib/sources/v1.ts`). The paths: `alliances/67111155`, `players/340581761349`, `alliances/325/FGH`, `openapi.json`, `servers`, `servers/325`, `rankings`, `events`, `kvk`, `map`, `players`, `alliances`. Budget: at most 12 upstream attempts, counted before each is sent; a 401, 403 or 429 stops it. The 12 calls must fit above the squads read's reserve (`squadsReserve`) or none is made (`quota_low`); while the day's squads read is still `running` it makes no call (`squads_busy`). An `app_alerts` claim (id 5) makes it run at most once. The window is outside every event window and both Raid Shield check windows (D137). What is stored: one `run_logs` line per path (`api.probe.path`) with its status and its JSON structure only (key paths, types, array lengths; numeric keys as `<numeric-key>`; a player's uid in a path as `[uid]`), cut at 16,000 characters per path, and one `api.probe` line with counts and a reason. No value from any answer is stored, logged or sent anywhere; the console gets one count line. Agents never read the key and never call the upstream themselves. A follow-up PR removes the code; the `run_logs` lines stay as any other run-log line.
