## D79 — The event page's live reads are shared between viewers in Next's data cache, tagged by event (2026-11-16, owner, 08zzzzj, issue #327)

Why: while an event runs, every viewer's page refreshes once per sample slot (`LiveRefresh`, D69), and each load read the event's progress (`eventProgress`) and, before the End, the turnout so far (`memberTurnoutSoFar`) from Neon. Neon's Free plan allows 100 CU-hours and 5 GB of transfer a month. Every viewer reads the same rows, and the rows change only when the collector writes.

- **What is cached.** Only database rows, per event: `progressRows` (the alliance totals of the Start and the samples, and the End's bare row; times as epoch milliseconds) and the result of `memberTurnoutSoFar` (no `Date` in it). A cached value goes through JSON, so nothing in it may be a `Date`.
- **What is not cached.** Everything that depends on `now` or on the environment: live or finished, the next reading and the refresh time, the overdue slot, the standings, the pulse and the busiest span. `eventProgressOf(rows, { now, everyMin })` (`lib/queries/live.ts`) computes them per request from the cached rows. A cache entry never freezes time.
- **Mechanism.** Next 16.4.5's `unstable_cache` with the tag `event:<id>`, and `revalidateTag(tag, { expire: 0 })`. `'use cache'` with `cacheTag` is the newer API but needs `cacheComponents: true` in `next.config.ts`, which this change does not touch. A module-level map in `lib/event-cache.ts` shares one read between the requests that miss the same key at the same time in one server instance: `unstable_cache` alone runs the read once per request on a miss, and viewers refresh in step (each slot + 60 s). `expire: 0` makes the next read after an invalidation wait for fresh rows instead of being served the old ones once.
- **Keys and safety net.** `progress` (the event has no End row) and `turnout-so-far` keep an entry at most `LIVE_MAX_AGE_S` = 60 s: the page looks for a slot's reading 60 s after the slot (`SAMPLE_WAIT_MS`), so all the viewers of one refresh share one read, and a missed invalidation shows rows at most a minute old (plus one request: an expired entry is served once while Next reads it again). `progress-done` (the End has a row) keeps an entry `DONE_MAX_AGE_S` = 1 day: no sample comes after the End, the only later writes are admin re-runs and renames, which invalidate, and a day bounds a missed one. The page picks the key from its own event detail, so when the End appears the page moves to the other key even if an invalidation was missed.
- **Invalidation** (INVARIANT `cache.write-invalidates-event`). Through the injection point: `AppContext.eventCache.invalidate(eventId)`. `lib/run.ts` (`collect`) calls it after every run that claimed a row (a sample, the Before, the After, a forced re-run, D63's re-read of stale rows), after the row is final. `POST /api/manual-event/rename` and `POST /api/manual-event/settings` (visibility decides `publicEvent`) call it after their write. The collector and `lib/repo` do not import `next/cache`. Not invalidated: `pruneRehearsals`, the only delete of an event, because a rehearsal is never public, so its entry is always null, and an event id is never reused.
- **Tests.** Next's cache needs a Next request (`incrementalCache` and the work store), so it cannot run under vitest. `EventCache` is the interface; `memoryEventCache()` (`lib/app-context.test-helpers.ts`, JSON round trip, no expiry) is the tests' implementation in `testContext`.
- **Measured** (scratch Postgres 18 with `pg_stat_statements`, seed event 3 with 15 samples, `next build` + `next start` of the commit before and after, 20 concurrent `GET /events/3`): finished event, statements 240 before, 221 after (cold), 220 after (warm); progress reads 20 → 1 → 0. Live event, statements 240 before, 164 after (cold), 160 after (warm); progress reads 20 → 1 → 0, turnout-so-far reads 20 (3 statements each) → 1 → 0. The progress read returns about 320 rows per call for this event.
- **Checked on `next start`.** A sample deleted with SQL stays hidden until `POST /api/manual-event/rename` invalidates the event; the next load shows it. With no invalidation, the first load after 60 s still gets the old rows and the one after it the new ones.
- **Not cached.** The rest of the event page's reads (8 statements per load for a live event, 11 for a finished one: the event list, the event detail, names, ranks, movers, roster changes, End turnout). They are the same for every viewer and could use the same cache later.
