## D65 — Avatar frames: an id per member row, one picture per frame (2026-11-14, owner, 08zzzr)

Why: the owner asked for the game's avatar frame around every player photo, as the game shows it. Every `/v1` member already carries `frame_url`, which D22 dropped from `raw_json`. No extra upstream call is needed.

- **What the upstream sends.** `frame_url` is a path relative to the tracker site, `/static/frames/frame_<id>.png`. In the recorded fixtures (30 alliance bodies, 2,723 member rows, 2026-11-04) every member has one, and there are 6 distinct ids: 5001 (2,395 rows, 88 %, the game's plain silver frame), 5010 (180), 5026 (140), 5008 (6), 5009 (1), 5007 (1). The internal source sends the same field.
- **The files (one plain GET each, 2026-11-14, our User-Agent, like D22's badge check).** All six are 190 × 190 PNGs with alpha, 5–24 KB, `Last-Modified` Mon, 31 Aug 2026 for all six, origin `Cache-Control: max-age=14400`. Measured from the alpha channel: the photo's hole is the middle 120 × 120 (a square with slightly rounded corners); the ornaments reach the edges and, on 5007, 5008 and 5010, a little into the hole.
- **Storage (owner: store the distinct frames, not one per player).** Each `member_snapshots` row gets `frame_id integer` (migration 0015), the number from the file name. The picture itself is stored nowhere: `/img/frame/[id]` fetches it from the tracker site's origin and the CDN keeps it for a year (`FRAME_CACHE` = `BADGE_CACHE`), so each distinct frame is fetched about once per CDN region. Compared:
  - an id per row (chosen): 4 bytes per member row, ~16 KB a week at 20 alliances × 100 members × 2 phases; a new or temporary frame shows up with no change on our side;
  - the frame URL per row: about 30 bytes per row for the same information;
  - the frame images in a table of our own (~100 KB for six): no dependency on the tracker site at view time, but a fetch-and-store step in the collector and a database read per image the CDN misses. Not worth it while the CDN holds each frame for a year;
  - the PNGs in the repository: a new or temporary frame would not show until someone adds its file.
- **Parsing.** `frameId()` in `lib/sources/shared.ts` accepts only `/static/frames/frame_<digits>.png`; any other value, or none, is null. A missing frame never fails a run (cosmetic, like the photo).
- **Route.** `/img/frame/[id]`: digits only (1–9), `frame_<id>.png` on the origin of `LAP_SITE_BASE_URL`, the D22 fetch rules (5 s, no redirect, 1 MB cap, raster only, our User-Agent, no Origin/Referer/cookies), served as fetched (no redraw: the file is 190 px and pages draw it at most 80 px). Failure: bodyless 404, one `image.fetch_failed` warn line (D22 amendment, issue 126). Queries return `frameId`, never a URL.
- **Where it shows.** `PlayerAvatar` everywhere a photo shows: member rows and cards, player search, leadership, the player page, player and member compare. With a frame: the game frame replaces the soft drawn frame, the photo (or `NoPhoto`) sits in the hole. Small: 51 px box, so the photo keeps its 32 px. Large: 80 px box, a 50 px photo (89 px would keep 56 px, but a 16-letter name beside it then wraps at 360 px). A frame that fails to load leaves the photo alone. Rows stored before the column (`frame_id` null) keep the drawn frame.
- **Freshness.** A frame is the one stored on that member row, like the photo: event snapshots (weekly, plus manual rounds) bring a changed frame. The daily read (D60) stores no photos and no frames. Rows stored before this change have no frame, and `raw_json` never kept `frame_url`, so there is no backfill: frames appear from the first snapshot after the deploy.
- **Not done:** frames in the Discord event picture and in the link preview (D22 amendment, 2026-11-14), frames from the daily read.
