## D73 — Workspace sign-in: the choices D71 left open (2026-11-16, 11c, issue #295)

D71 sets the rules of the workspace sign-in. This records only what it left to the implementation.

- **One callback for every workspace.** Discord's redirect URI is `/api/w/auth/callback`, the same for every alliance, so a new workspace needs no change in the Discord application. The slug travels in `state` (`<slug>.<32 random bytes, base64url>`), and is used only after the state matches its cookie in constant time. The slug `auth` is refused, because `/api/w/auth/...` is the callback's own path. The Discord application lists two redirects: `https://laptracker-inky.vercel.app/api/w/auth/callback` and `http://localhost:3000/api/w/auth/callback`.
- **Login and logout paths.** `GET /api/w/[slug]/login` sets the state cookie and redirects to Discord; `?silent=1` sends `prompt=none` (the re-authorisation after 24 hours, which `/w/[slug]` starts by itself when it finds an expired session). The button's sign-in sends `prompt=consent`. `POST /api/w/[slug]/logout` with a JSON body `{}`.
- **The Discord base URL is an env var.** `DISCORD_API_BASE_URL`, default `https://discord.com/api`, is the base of the authorize page, the token exchange and the two reads, so tests and the local e2e point it at a stub. No test or e2e calls the real Discord.
- **Cookie names.** Session: `__Host-lap_ws` (24 h at most). State: `__Host-lap_ws_state` (10 min). Both `Path=/; HttpOnly; Secure; SameSite=Lax`; browsers accept `Secure` on `http://localhost`. Language: `lap_ws_lang` (`en`, `pt-BR`, `fr`; one year, written by the EN · PT · FR switch), separate from the public `lang` cookie. One session cookie per browser: signing in to a second workspace replaces the first one's session cookie.
- **The rate limit key.** A bad state counts under `w:ip:<address>` in `auth_attempts`, with the PIN's per-IP limits (5 per 15 minutes); at the limit the callback answers 429 before reading the state. The PIN's own `ip:` key is untouched, so a bad state never locks the owner's PIN.
- **Who is stored.** A `workspace_users` row is written when someone gets in (display name: the server nickname, else the Discord display name) or when the owner allowlists an account. A refused account leaves no row.
- **The `/admin` card.** A "Workspaces" section at the end of `/admin` (PIN, English, D48) lists each workspace with its server id, role ids, open sessions and allowlist, and has three actions, each a PIN route: `POST /api/admin/workspaces` (add or edit; one workspace per alliance, so saving again for the same union id edits it; 409 `slug_taken`), `POST /api/admin/workspaces/allowlist` (a Discord user id until the end of a date, UTC; `allowlist_added_by` is `admin`), and `POST /api/admin/workspaces/sign-out` ("Sign out everyone in this workspace"). No workspace is seeded: the owner registers OGs on the card (issue #295 said "OGs seeded"; the server and role ids are data, not code).
- **No-access reasons.** The callback sends a refused account to `/w/[slug]/no-access?why=` with `not_member` (not in the alliance's Discord server), `no_role`, `allowlist_expired` or `blocked`. The page explains each in the officer's language and reads nothing.
- **Session end.** A session ends after 24 hours. For an account let in only through the allowlist, it ends earlier if the allowlist entry ends first. Making a new session deletes every session already past its end.
- **Revocation, for now.** "Sign out everyone in this workspace" and the allowlist expiry are the only ways to take access away. `workspace_users.blocked` is kept and checked at sign-in and on every request, but nothing sets it yet.
- **Headers.** Every `/api/w/...` answer carries `Cache-Control: private, no-store`, set by the handler and by `proxy.ts`. The proxy's header also holds on `/w/...` pages in a production build (`next build` + `next start`, 2026-11-16: `/w/ogs` and `/w/ogs/no-access` answered `cache-control: private, no-store`; a public page answered Next's own `private, no-cache, no-store, max-age=0, must-revalidate`). `next dev` answers `no-store` instead.
- **No link preview.** The `/w/[slug]` layout sets `openGraph: null` and `twitter: null`. The rendered head of a production build has no `og:` or `twitter:` tag on `/w/ogs`, while `/` carries the root `og:image`.
- **Deviation: the upstream banner reads before the access check.** The root layout's `UpstreamBanner` reads the public upstream status from the database on every page, `/w/...` included, before the page's own access check. It reads only public data (whether the game's API is answering), and none of it reaches the metadata. Keeping `/w` out of it would need separate root layouts.
- **The roster-field fence test** (`lib/private/roster-fields.test.ts`) scans `app`, `lib`, `config`, `scripts` and `proxy.ts`. Its exemptions: `lib/repo`, `lib/private`, `lib/collector*.ts`, `lib/raw-json.ts` and the list itself (`lib/queries/blocked-keys.ts`). Its limit: `online`, `last_online_at`, `joined_at`, `daily_honor` and `daily_tech` are matched as a property, a key or a string, but `x`, `y` and `active` only as string literals. As `.x` or `active:` they are everyday drawing, date and CSS code, so a text scan cannot tell them from a roster read. Comments are not scanned.

**Amendment (2026-11-17, 11z, D105).** The `/admin` button "Sign out everyone in this workspace" now reads "Sign out everyone, including me", in a danger style, after "Sign out members only (officers stay signed in)" (D105). What it does is unchanged.

**Amendment (2026-11-17, 11z2, D105).** "Sign out everyone, including me" and "Sign out members only (officers stay signed in)" are now one button, "Sign out users", whose sheet picks everyone, officers only, members only or one person and then confirms with the count (D105). Everyone still ends every session of the workspace; the owner's `/admin` PIN is not one of them.

**Amendment (2026-11-17, 11z3, D105).** The no-access reasons are now `not_member`, `no_role`, `board_closed`, `allowlist_expired` and `blocked`. `no_role` means in the server without a leadership role and without one of the workspace's member roles. `board_closed` means the same while the workspace has no member role set, so the members' board is closed. The `/admin` card also lists each workspace's member role ids, or "Members' board is off until you set a member role.", and the add-or-edit form takes them (D105). That form now loads the picked workspace's current settings (pick the workspace, or its alliance; "New workspace" starts empty), so saving one changed field keeps the others.

**Amendment (2026-11-19, 11aw, D126).** `POST /api/admin/workspaces` also answers 409 `guild_taken` ("Another workspace already uses this Discord server.") when another alliance's workspace has that Discord server id: one workspace per server, also a unique index on `workspaces.discord_guild_id`.

**Amendment (2026-11-20, issue 451, D129).** `DISCORD_API_BASE_URL` is also the base of the bot's install link (`/oauth2/authorize`), of Check's `GET /guilds/{id}` with the bot token and of the webhook check `GET /webhooks/{id}/{token}` in Alliance settings, so tests and the local e2e reach a stub for each. The test message and publishing still post to the saved webhook URL itself.

**Amendment (2026-11-20, issue 453, D130).** The one callback also finishes a sign-in through a new alliance's invite link: a state starting `invite.` goes to `finishInviteSignIn` (scopes `identify guilds`, the same state cookie, the same per-IP limit for a bad state), which redirects to `/w/invite`. `invite` and `request` are reserved slugs beside `auth`, since `/w/invite` and `/w/request` are a new alliance's pages. /admin's add-or-edit form stays for the manual way.

**Amendment (2026-11-20, issue 457, D131).** "One session cookie per browser" is replaced: each workspace has its own session cookie, `__Host-lap_ws.<slug>`, so signing in to a second workspace keeps the first. The old `__Host-lap_ws` is still read until its sessions end, never written. The one callback also finishes the sign-in chooser at `/w`: a state starting `w.` goes to `finishChooserSignIn` (scopes `identify guilds.members.read guilds`), with the same state cookie and per-IP limit.
