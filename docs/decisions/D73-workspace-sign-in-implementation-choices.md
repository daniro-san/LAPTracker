## D73 — Workspace sign-in: the choices D71 left open (2026-11-16, 11c, issue #295)

D71 sets the rules of the workspace sign-in. This records only what it left to the implementation.

- **One callback for every workspace.** Discord's redirect URI is `/api/w/auth/callback`, the same for every alliance, so a new workspace needs no change in the Discord application. The slug travels in `state` (`<slug>.<32 random bytes, base64url>`), and is used only after the state matches its cookie in constant time. The slug `auth` is refused, because `/api/w/auth/...` is the callback's own path. The Discord application lists two redirects: `https://laptracker-inky.vercel.app/api/w/auth/callback` and `http://localhost:3000/api/w/auth/callback`.
- **Login and logout paths.** `GET /api/w/[slug]/login` sets the state cookie and redirects to Discord; `?silent=1` sends `prompt=none` (the re-authorisation after 24 hours, which `/w/[slug]` starts by itself when it finds an expired session). The button's sign-in sends `prompt=consent`. `POST /api/w/[slug]/logout` with a JSON body `{}`.
- **The Discord base URL is an env var.** `DISCORD_API_BASE_URL`, default `https://discord.com/api`, is the base of the authorize page, the token exchange and the two reads, so tests and the local e2e point it at a stub. No test or e2e calls the real Discord.
- **Cookie names.** Session: `__Host-lap_ws` (24 h). State: `__Host-lap_ws_state` (10 min). Both `Path=/; HttpOnly; Secure; SameSite=Lax`; browsers accept `Secure` on `http://localhost`. Language: `lap_ws_lang` (`en`, `pt-BR`, `fr`; one year, written by the EN · PT · FR switch), separate from the public `lang` cookie. One session cookie per browser: signing in to a second workspace replaces the first one's session cookie.
- **The rate limit key.** A bad state counts under `w:ip:<address>` in `auth_attempts`, with the PIN's per-IP limits (5 per 15 minutes); at the limit the callback answers 429 before reading the state. The PIN's own `ip:` key is untouched, so a bad state never locks the owner's PIN.
- **Who is stored.** A `workspace_users` row is written when someone gets in (display name: the server nickname, else the Discord display name) or when the owner allowlists an account. A refused account leaves no row.
- **The `/admin` card.** A "Workspaces" section at the end of `/admin` (PIN, English, D48) lists each workspace with its server id, role ids, open sessions and allowlist, and has three actions, each a PIN route: `POST /api/admin/workspaces` (add or edit; one workspace per alliance, so saving again for the same union id edits it; 409 `slug_taken`), `POST /api/admin/workspaces/allowlist` (a Discord user id until the end of a date, UTC; `allowlist_added_by` is `admin`), and `POST /api/admin/workspaces/sign-out` ("Sign out everyone in this workspace"). No workspace is seeded: the owner registers OGs on the card (issue #295 said "OGs seeded"; the server and role ids are data, not code).
- **No-access reasons.** The callback sends a refused account to `/w/[slug]/no-access?why=` with `not_member` (not in the alliance's Discord server), `no_role`, `allowlist_expired` or `blocked`. The page explains each in the officer's language and reads nothing.
- **Headers.** Every `/api/w/...` answer carries `Cache-Control: private, no-store` (set by the handler and by `proxy.ts`). On pages, Next sets its own `Cache-Control` for a dynamic render, which also has `no-store` (`next dev` sends `no-store`).
