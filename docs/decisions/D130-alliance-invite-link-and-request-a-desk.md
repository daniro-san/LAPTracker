## D130 — A new alliance gets its Desk by itself: the owner's one-time invite link (server and roles picked from lists, or the roles created), and "Request an Officers' Desk" with a roster check (2026-11-20, owner, issue 453; amends D73, D101, D126)

Why: creating a workspace needed the alliance's Discord server id and role ids, copied by hand and typed on /admin by the owner (D73). The owner (issue 453 and its comments of 2026-11-19 and 2026-11-20): a one-time link where the alliance's leader picks the server and the roles from lists, or creates the roles; and a request form, so an alliance can ask instead of waiting.

**The invite link.**

- **/admin → New alliances → "Invite an alliance"**: the owner picks a tracked alliance that has no workspace and taps "Create the invite link". The answer shows the link once, with Copy: `https://<site>/api/w/invite/<id>.<secret>`, 32 random bytes. Only the secret's sha256 is stored (`alliance_invites.token_hash`). It works once, for 7 days. A new link for the same alliance cancels the earlier one; "Cancel the link" stops one at once. Each line shows the link's state: not used yet, "<Discord name> signed in", "picked the server; roles next", used (`/w/<slug>`), expired or cancelled.
- **Opening it**: `GET /api/w/invite/<id>.<secret>` trades the secret for an HttpOnly `__Host-lap_invite` cookie (1 day) and redirects to `/w/invite`, so the secret is never in the page's address, a Referer or analytics. The secret is compared with `timingSafeEqual` on its sha256. A wrong link counts under the IP like a bad sign-in state (D73: 5 per 15 minutes) and goes to `/w/invite?e=link`.
- **`/w/invite`**, four numbered steps, each with a tip, in EN, PT-BR and FR (`lib/private/dictionary.invite.ts`, `dictionary.invite-fr.ts`):
  1. **Sign in with Discord**, scopes `identify guilds` (`GET /api/w/invite/login`), through D73's one callback: the state starts with `invite.`, so the callback sends it to `finishInviteSignIn`. The callback reads `/users/@me` and `/users/@me/guilds` once, on the server, and keeps with the invite only the servers she owns or where Discord gives her Manage Server or Administrator (`owner`, permission bits 0x20 and 0x8), as id and name. The Discord token is not kept. The browser gets a claim cookie `__Host-lap_invite_who` (1 day, only its sha256 stored); every step after needs it.
  2. **Pick your alliance's server** from that list. A server another workspace uses shows "Already has a Desk" and is refused (409 `taken`, D126's unique server). A server not on her list is refused (403 `not_yours`).
  3. **Add LAPTracker to the server**: D129's install link (`installUrl`) for the picked server, then "I added it: continue", which reads the server's roles with the bot token (`GET /guilds/{id}/roles`). 403 or 404: "LAPTracker is not in your server yet…" and the step waits. No step polls: each check is one tap, and every step counts toward 30 per 15 minutes per invite.
  4. **Choose who gets in**: the server's roles by name and colour (not @everyone, not a bot's own role), the leadership roles (one or more) and the member roles (optional, D105). No id is typed. "To give a role in Discord: Server Settings → Members → the person → the + under their name."
  - **Or create the roles** ("No roles for this yet? Create them here", owner's comment of 2026-11-19): names prefilled `[TAG] Leadership` and `[TAG] Members`, with the invite's alliance tag from `config/alliances.ts` (never OGs' unless the invite is OGs'), both editable. First "Allow LAPTracker to create roles", a second install link for this server only with D101's permissions plus Manage Roles (268435456): `309506083840`. Then "Create the roles": `POST /guilds/{id}/roles` with `permissions: "0"`, not mentionable, not hoisted. "Give me the leadership role" (ticked by default) is `PUT /guilds/{id}/members/{her id}/roles/{role}`. If Discord refuses the create (403): "Discord said no: LAPTracker may not create roles yet…", and picking stays. If it refuses the give (the bot's role is lower): "LAPTracker could not give you the role…", and she still gets in. The default install (D129) never asks for Manage Roles.
- **"Open our Officers' Desk"** (`finish`): the server's roles are read again and every id sent must be one of them (400 `bad_role`). One transaction marks the invite used (only while open, so it works once), inserts the workspace (never an edit: an alliance with a workspace gets 409 `has_desk`, a server or address taken meanwhile 409 `taken`), and her `workspace_users` row, allowlisted with `allowlist_added_by = 'invite'` and no end. The server list is dropped from the invite. Then the bot is marked seen (D129), the commands that are on are registered in her server (`syncCommands({ only })`; a refusal leaves Check in Alliance settings), and an officer session is made (D99), so she lands on her Desk signed in.
  - **The address**: the tag in lowercase letters and digits (`wack`), then `-2` … `-9` while taken; a tag with fewer than two such characters gives `a<union id>`. `invite` and `request` are now reserved slugs, like `auth`.
  - **Why the allowlist with no end**: she gets in even before she holds the leadership role, and the person who set up the Desk is not locked out later. The owner sees the entry on /admin's allowlist line.
- **One account**: until a server is picked, signing in with another account replaces the first (a wrong account is fixed by "Use another account"). After it, another account gets `/w/invite?e=claimed`.

**Request an Officers' Desk** (`/w/request`, no account; the owner's comment of 2026-11-20).

- The alliance (the tracked alliances; issue 459's ranks-board list replaces it when it lands), the name in the game, and "I'm the alliance leader (R5) or an R4" with R5 or R4. Without the tick the form says "A Desk is requested by the alliance's leadership. Ask your R5 or an R4 to send this." and sends nothing.
- `POST /api/w/request`: same origin, JSON, at most 3 a day per address and 30 a day for the site (`auth_attempts`, `day:` keys). An alliance that has a workspace gets 409 `has_desk`.
- **The roster check** never blocks. The name's `nameKey` is matched against the alliance's newest roster of any kind (D72's daily read, or an event's); the rank is the daily read's `rank_label`, else R1–R5 from `rank_code`, else a Start or End's. Kept: the alliance, the name typed, the rank claimed, `found` or `not_found`, the roster's rank and when it was read. No other roster field (D71). /admin shows "Roster says: R4 · Recruiter, seen 19 Nov" or "Name not found in the roster".
- **The owner is told**: one line on `NOTIFY_WEBHOOK_ADMIN`, "Desk requested: [TAG] Name · <name> says R5 (leader) · Roster says: …", with Discord markdown escaped and no mention possible.
- **The requester's way back** is a random status secret (`<id>.<secret>`, only its sha256 stored) in an HttpOnly `__Host-lap_request` cookie (45 days), and the same as a link they can keep (`/api/w/request/<id>.<secret>`, counted like a wrong invite link when wrong). `/w/request` shows only that request: waiting, approved ("Continue"), or not approved with the owner's reason.
- **The owner decides on /admin → New alliances**: "Approve and make the link" creates the same invite link for that alliance (shown once, to send in Discord or game mail) and marks the request approved; the requester's "Continue" (`/api/w/request/continue`) opens that invite with their status secret (`r.<id>.<secret>`), so they need no second link. "Decline" takes an optional reason shown to them.
- **Retention**: a decided request, and a used, cancelled or expired invite, is deleted 30 days after (`purgeOldInvites`, on every /admin invite call and every new request). Neither table belongs to a workspace (no `workspace_id`; the invite keeps the made workspace's slug as text), so D125's purge and download do not list them.

**New workspaces start with the defaults** (D126): no `workspace_features` row is written, so a workspace made from an invite has the defaults for a new alliance (the free features on, the paid ones off) until the owner changes them.

**Analytics** (issue 486, `docs/analytics/tracking-plan.md`): `ws_access_requested` (`claimed_role`, `roster_match`), `admin_workspace_approved` (an invite link made or a request approved), `ws_invite_opened` (the page before sign-in), `ws_invite_completed` (`roles_created`). Never a name, a server or an id. `/w/invite` and `/w/request` carry no `workspace` property (`areaOf`).

**Storage** (migration `0052_alliance_invites`): `alliance_invites` (alliance, token hash, created, expires, cancelled, the account that signed in and its Discord name, the claim's hash, the servers she may pick, the server picked, used, the slug made) and `access_requests` (alliance, name, rank claimed, roster match, roster rank and date, status hash, created, decision, decided, reason, the invite).

**Routes**: `GET /api/w/invite/[token]`, `GET /api/w/invite/login`, `POST /api/w/invite` (`server`, `roles`, `create_roles`, `finish`), `POST /api/w/request`, `GET /api/w/request/[token]`, `GET /api/w/request/continue`, and `POST /api/admin/invites` (PIN: `create`, `cancel`, `approve`, `decline`). Errors are codes only. Every `/api/w/...` answer is `private, no-store` (D73).

**The manual way stays**: /admin's add-or-edit workspace form (D73) is unchanged.

**Owner steps.**

1. Nothing new in Vercel or in the Discord application: the redirect URI is D73's one callback, the scopes `identify guilds` need no setting, and Public Bot is already on (D129).
2. For a new alliance: /admin → New alliances → Invite an alliance → Copy, and send the link to its R5 or R4. Or approve its request there.
3. After the Desk exists, turn on its paid features on its card if the alliance should have them (D126).

The roster check keeps rank and date only and never blocks; 3 a day per address; an alliance with a workspace is told so; an approved request's status secret opens its invite (`lib/private/access-request.test.ts`). The /admin route: PIN only, the link answered once and stored as a hash, a new link cancels the earlier one, approve makes the link once, an alliance with a workspace gets none (`app/api/admin/invites/route.test.ts`). Issue 471's suite: a taken server is refused, an invite never attaches to another workspace (its alliance's, or a server taken meanwhile) with the other workspace's rows unchanged, and a request's status secret opens only that request (`lib/private/invite-isolation.test.ts`).

**Amendment (2026-11-20, PR 499 review).**

- **Each step is bound to the account that claimed the invite.** Picking the server and using the link write only while the invite is still claimed by the same Discord account with the same claim (`heldBy` in `lib/repo/alliance-invites.ts`, inside the finishing transaction). A second account that signs in meanwhile makes the first browser's step change nothing.
- **Approve is one transaction.** The request is marked approved only while undecided, then its link is made and tied to it (`approveRequest`). A second, quick approve makes no link and cancels none. The actions moved from the route to `lib/admin-invites.ts`: not `lib/private`, which only `app/(private)` may import (D71).
- **The address limit is checked first**, so an address over its 3 a day never uses up the site's 30.
- **Creating the roles reuses a role of the same name** already in the server. If Discord creates the leadership role but refuses the member role, the page says so ("Discord did not create the member role. Tap Create the roles again: the leadership role is kept, not made twice.").

**Amendment (2026-11-20, issue 500, review of PR 499).**

- **A request never answered is deleted 30 days after it was sent** (`KEEP_MS`, the same 30 days as a decided one), by the same `purgeOldInvites` on every /admin invite call and every new request.
- **/admin lists the newest 50 requests** (`REQUESTS_SHOWN`), and under them "Showing the newest 50. Requests never answered are deleted after 30 days." when there are more. With 30 a day for the site and the purge above, at most about 900 rows can exist.
- **The owner's line when an alliance completes its Desk** (issue 453's "Home line"). There is no owner Home page, so it goes to the two owner places that exist: one line on `NOTIFY_WEBHOOK_ADMIN`, "Desk made: [TAG] Name now has its Officers' Desk at /w/<slug>. It shows on /admin#new-alliances.", sent by `POST /api/w/invite` after `finish` (a failed send changes nothing); and /admin → New alliances → Invite links, where a used link now reads "Desk made 20 Nov: /w/<slug>" (was "used: /w/<slug>").
- **A claimed R5 that the roster lists as R4** gets a highlighted line under the request on /admin: "Says R5, but the roster lists R4 · Recruiter. Worth a check before you approve." It never blocks or changes the request (D75).
- **On screens below 640 px, "No roles for this yet? Create them here"** comes before the two role lists on `/w/invite`, so a server without roles shows the way out first.
- **The Desk's tracker-key card on Home** (D124), while the alliance has no key of its own, says where to get one: "To get a key: sign in on the tracker's account page with Patreon, then copy the key that starts with lap_.", with a link "Open the tracker's account page" (`/account` on `LAP_SITE_BASE_URL`'s host, a new tab). EN, PT-BR and FR.
