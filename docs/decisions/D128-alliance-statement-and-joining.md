## D128 — The public alliance page shows the alliance's in-game statement and how to join, from the daily read (2026-11-19, owner, issue 479; amends D72, D22 and plan §6)

Why: the owner (issue 479) wants each alliance's own statement on its public page, with its joining rules. `GET /v1/alliances/{id}` already returns them, so the card costs 0 extra upstream calls. Plan §31 said `declaration`/`bulletin` were "not shown in v1"; this decision shows them.

- **Storage.** `trimRaw` (`lib/raw-json.ts`) no longer drops `declaration` and `bulletin`: they stay in `raw_json` for every read, daily and event (plan §6 and D22 said raw_json drops them; both are amended here). The rows stored before this change have no statement. The first daily read after deploy fills it. Size: the statements in `fixtures/v1-ids` are 0 to 756 characters (most under 300), stored twice because the game sends the same text in both fields. That is under 1.5 KB per roster against D72's ≈ 8.3 KB.
- **Read model.** `allianceStatement(db, unionId)` (`lib/queries/statement.ts`) picks only `declaration`, `bulletin`, `language`, `join.auto`, `join.power`, `join.castle_level`, `member_count` and `capacity` out of `raw_json` in SQL, from the newest `daily_rosters` row with no error and a response. `members`, `leader_id` and every roster field (D71) never leave the database. D72's "raw_json is never selected by a read model" is amended to "only these fields". A failed read keeps no response (D72), so the card falls back to the newest read that succeeded, and its date says which. An alliance with no such read (discovered alliances, #459) gets no card.
- **Values.** The text is `declaration`, else `bulletin`, trimmed at the ends. A whitespace-only text counts as none. `lang` is set only when `Intl.DisplayNames` names the code, so the game's `all` gets none. A `join.power` or `join.castle_level` of 0 means no minimum and is left out. Seats open = capacity − members, never below 0 (the game reports 101/100).
- **The card** (`app/_ui/AllianceStatement.tsx`, below the summary band on `/events/[id]/alliances/[unionId]`):
  - The joining line comes first: "By application · 8M+ might · HQ 14+ · Full (100/100)", or "27 seats open (73/100)" when there is room. "Open to join" replaces "By application" when `join.auto` is true, and the minimums still show, because the game applies them to open alliances too (one real alliance is open with HQ 15). Might uses the compact format (D78) with trailing zeros dropped, because a game minimum is a round number: "8M", "8.5M" (owner, 2026-11-20). The `+` marks a minimum, and "Full" replaces "0 seats open" (persona panel, 2026-11-19: without them, the figures read as the alliance's own might and the line read as broken). Each part stays whole, and the line breaks only between parts.
  - Then the text, under the label "Written by the alliance in game". It is plain text with its line breaks (`whitespace-pre-line`, `dir="auto"`, its `lang`), and it is never HTML, never Markdown and never a link. It sits within the 65-character measure (D122 `Measure`).
  - A text that may run past six lines at 360 px (a conservative estimate of 32 characters a line) is cut at six lines, with a real "Show all" / "Show less" button (44 px, `aria-expanded`). That one small client component hides the button where the text fits. A shorter text is rendered on the server with no script.
  - The last line is "As of {date}", the server day of the read used. With no text, the card is titled "Joining" and holds the joining line alone.
- **Not done.** The statement is not translated (Groq), as the issue scopes it. The history page `/alliances/[id]/history` does not show the card.
