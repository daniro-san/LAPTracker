## D74 — Screenshot reader: free OCR with Tesseract.js, English data committed, no image library (2026-11-16, owner, 11d, issue #299)

Why: the leadership's lists (Alliance Duel and Donation rankings, the Secret Operations report) exist only as game screenshots. The owner asked to validate a free option first (issue #299); Tesseract.js read 38 of 38 ranking rows with exact numbers on the shared pictures, and nothing here sends a picture to a paid service. This is the engine only: `lib/screenshot/`, no route and no page. The upload and review screen come after the workspace sign-in (D71).

- **Package.** `tesseract.js` 7.0.0, Apache-2.0, published 2025-12-15 (`pnpm view tesseract.js time`; latest on 2026-11-16). Pinned exactly. It adds 13 packages. The one that matters is `tesseract.js-core` 7.0.0 (2025-12-15), the WebAssembly build of Tesseract: 45 MB unpacked, six `.wasm` variants of which the worker loads one by CPU features. Newest transitive: `wasm-feature-detect` 1.10.1, published 2026-11-11 (five days before this decision); the lockfile pins it.
- **Install scripts (D10).** One: `tesseract.js` has `postinstall: opencollective-postinstall || true`, which only prints a donation notice. It is denied in `pnpm-workspace.yaml` (`allowBuilds: tesseract.js: false`). The other twelve packages have no install script (pnpm asks about none). The OCR needs no script: it runs from the package's files.
- **Language data: committed, no network at run time.** `lib/screenshot/tessdata/eng.traineddata.gz` is the `4.0.0_best_int` English model from `@tesseract.js-data/eng@1.0.0` (the file Tesseract.js downloads from jsDelivr by default). 2,952,873 bytes gzipped, 5,199,098 bytes loaded; sha256 of the gzip `45b4cb346724ac1774f1c36f42f182b887bcdb28ebe63e6fff90ac41f3fcff91`, of the loaded file `5dc5d8d640a212c9d6184921ba103b186f50e0fed9ee716c53e6b312b400d747`. Without a `langPath` and `cacheMethod: "none"` Tesseract.js downloads the data at run time and writes a cache file in the working directory, which a Vercel function cannot do and which would make every cold start depend on a CDN. `read-screenshot.ts` passes both. A committed file rather than the `@tesseract.js-data/eng` package (13.9 MB unpacked, five variants, last published 2023) or a build-time download: one file, one hash, no extra dependency.
- **No Cyrillic data.** Measured on the three pages with Cyrillic names, English alone against English + Russian: Russian turned two names from garbage into near-Cyrillic text (both `unsure` with the right member suggested instead of `none` and `unsure`) and one Latin name into Cyrillic letters, cost 2.7 MB more data and up to twice the time on one page. `nameKey` already folds Cyrillic look-alikes to Latin on both sides, so the roster match repairs the rest. Not worth it; a later decision can add it.
- **No image library.** The validation preprocessed with `sharp` (crop, greyscale, twice the width). Measured here: the enlargement is what matters (a 358 px page read as it is gave 2 of 8 rows and lost the medal rows; a crop without enlarging was worse; greyscale at twice the width read all rows, cropped or not), and cropping does not. `lib/screenshot/prepare.ts` decodes a PNG with `node:zlib`, converts to grey, resizes to 716 px wide (bilinear up, box average down) and encodes a grey PNG: about 150 lines, no dependency. On the 12 committed pictures it matched the `sharp` Lanczos result (rows found 88 of 88 against 89, numbers 87 against 88, no wrong name either way). A 1170 px phone-size PNG is brought down to the same text size: 8 of 8 rows (page 27), 8 of 8 (page 28), 7 of 7 (page 22). The same images unprepared read 8, 6 and 7 rows, and took 1.6 times as long on two of the three (under load). Anything that is not an 8-bit non-interlaced PNG is passed to Tesseract unchanged; a JPEG of 1170 px read 8 of 8 rows unchanged, a small JPEG would not be enlarged.
- **Server-side cost (measured, Node 26, macOS, 10 cores, load average 25-35 from other agents).** Worker start with the English data 0.14 s in the lightest run, 8 s in the heaviest. A page took 0.4-1.1 s in the last run (mean 0.66 s over the 13 pictures with one worker, load average 23-36) and up to 27 s in the heaviest run. Peak resident memory of the whole process, including `tsx`: 145-178 MB. Vercel's CPUs are not shared like this machine's, so the idle figures are the likely ones; they are not measured on Vercel. A function that reads several pages should open one reader (`openScreenshotReader`) and keep it for the request.
- **Not verified: bundling on Vercel.** The route session must ship the worker script, `tesseract.js-core` and `lib/screenshot/tessdata` with the function (`serverExternalPackages` and `outputFileTracingIncludes`), and check the function size against the 250 MB limit (45 MB of core plus 3 MB of data) and the 120 s `maxDuration` of D6. `read-screenshot.ts` finds the data folder from the working directory, not from `import.meta.url`, because bundlers rewrite that.
- **Accuracy on the 12 committed pictures (real OCR):** 88 of 88 rows on screen read, numbers exact for 87, ranks right for all, and no name matched to the wrong member. This table is a one-off measurement, run by hand with truth typed from the pictures; no test repeats it. What the tests guard: the parsers on the recorded text of all 12 pictures, the name matcher on the names read from pages 28 and 31 (no name matched to a member it does not belong to, at least ten matched), and `OCR_TEST=1` on pages 27, 22 and 53. A Discord post screenshot was tested locally and not committed: it shows a private chat and the repository is public.
- **Boundary.** `readScreenshot` takes the picture's bytes only. Tesseract.js would also accept a path or a URL string and fetch it; the wrapper never passes one. Picture bytes stay in memory and are not stored.
- **Names stay public game names.** The recorded OCR text and the screenshots in `fixtures/screenshots/` hold player names and alliance tags that anyone in the game can see; they hold no roster field that D71 blocks (no position, no online time, no photo URL).

**Amendment 2026-11-27 (owner, issue 617): no real game screenshot in the repository, and invented names in the fixtures.** The owner decided that the rule "invented names only, never a real game screenshot" (CONTRIBUTING.md, "The repo is public") holds with no exception, so this decision's "Names stay public game names" line no longer holds. The 12 game screenshots are removed from `fixtures/screenshots/`. Their recorded OCR text files stay as parser fixtures, with every player name and every other alliance's tag replaced by an invented one of the same shape (length, case, digits, joiners, and the same misreads); line order, numbers, ranks, badges and OCR noise are unchanged. They are no longer what the OCR reads from a committed picture. The name matcher's tests read an invented 101-name roster (`fixtures/screenshots/roster.json`) in place of the recorded `/v1` roster. `OCR_TEST=1` now reads three synthetic screens drawn with invented names (an Alliance Duel page, a Donation page, a Secret Operations report), and compares with the text the OCR recorded from them on 2026-11-27. The names quoted in the "No Cyrillic data" line were removed. The accuracy figures above were measured on the removed pictures and are kept as a record. Git history still holds the removed files.
