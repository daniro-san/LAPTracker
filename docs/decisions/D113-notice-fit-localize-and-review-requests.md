## D113 — Notices: "Fit to 1,000", Translate localizes within the board's room, and review requests between officers (2026-11-17, 11ad, issue #402; amends D81)

Why: a notice over the game board's 1,000 characters was cut when copied, and translations often came back longer than the source. The owner asked for a way to shorten a text without losing its key points, for Translate to write as a native officer would within the room, and for a light way to ask another officer to check a language (issue 402; owner comment of 2026-11-17: approve, or edit and save; no comment thread).

**Fit to 1,000** (`fitText`, `fitSystem` in `lib/ai/notice-writing.ts`; `kind: "fit"` on `POST /api/w/[slug]/notices/draft`).

- The button sits beside Translate and Improve writing on any language tab whose text is over `NOTICE_LIMIT` (counted with `noticeLength`, graphemes). Under them on a phone, beside them from 640 px. Hidden otherwise; the route refuses a text within the limit with 400.
- The answer is a draft ("Draft from Fit to 1,000, not saved") with Accept and Undo, like Improve writing. It is one Groq request through the same route and models, so it uses the same free-tier quota (D81); there is no separate counter.
- The prompt keeps every date, day, time, name, number, place and call to action, cuts repetition, greetings and filler first, adds nothing, and keeps D81's term rules and D75's people-first line. It writes in the tab's language in that language's officer voice (below), so Fit on a translated tab uses that language's localizer voice.
- Budgets: the first request asks for 95 % of the limit (950). If the answer is still over 1,000, one more request asks for 80 % (800). If that is over too, the route answers 422 `still_over` and the editor shows "Fit could not get this text within the limit. Your text is unchanged: shorten it by hand, or try again." The officer's text is not touched. Worst case is four model calls (two tries, each with its fallback), inside the route's 90 s.
- Logs: `notices.fit.ok` (ms, retried), `notices.fit.still_over` (ms). Never the text.

**Translate localizes** (`localizeSystem(to, limit)`).

- The notices' Translate now sends a system prompt per target language: "You localize alliance notices into …", with a voice line for each language (Brazilian Portuguese as a Brazilian officer writes it to the members, "vocês", never European Portuguese; French as a French-speaking officer writes it, « vous »; English plainly). Rules added before D81's: localize, do not translate word for word; keep every key point; keep the register; game terms as the alliance uses them (the game's own word where `TRANSLATED_TERMS` gives one, D52); no machine-translated or AI-sounding phrasing, and no greetings, sign-offs, emoji, headings or filler the text does not have; stay within 1,000 characters, and say the same key points in fewer words if a full translation would not fit.
- D81's rules stay as they were: the `<text>` block and its neutralising (D101), the data-only line, the glossary, the do-not-translate list, the weekday and heading rules, the worked example, the "mostly untranslated" retry. The request still carries only the officer's text.
- Discord's "Translate for me" (D101) keeps `TRANSLATE_SYSTEM` unchanged: `translateText` uses the localizer only when given a limit, which only the notices route passes.
- **A fitted translation stays linked to its source** (coordinator, 2026-11-17). Fit on a translation made in this editor keeps its "translated from" link, so the save takes that source's basis and does not mark the other languages out of date, and Translate from that tab still refills it from the source. Fit on hand-written text behaves like Improve writing: the text becomes the officer's own.
- A translation that still comes back over the limit is shown as it is, with the counter in red and Fit beside it. Translate does not call Fit by itself.

**Review requests** (`lib/private/notice-reviews.ts`, `POST /api/w/[slug]/notices/reviews`, migration `0038_notice_reviews`).

- On a notice's page, "Ask for a review" opens a sheet: what (the whole notice, or one written language) and who (anyone on the team, or one officer). The officers listed are the workspace's users with an officer session on record who are not blocked, without the one asking.
- `notice_reviews` keeps each request (notice, language or null, reviewer or null for the team, who asked, when) under the sheet's request id (D100). `notice_review_outcomes` keeps how it ended ("approved" or "edited", who, when), one per request, under its own request id. Neither table is ever updated.
- Who answers: the named officer; for a team request, any officer but the one who asked. Others get 403 `not_reviewer`; a second answer gets 409 `closed`; a repeat of the same answer's request id gets 200.
- The request shows at the top of the notice ("Review asked by Ana · PT", then "For you · …", "For Rook · …" or "For the team · …"), with Approve and "Edit and save" for whoever may answer. "Edit and save" opens the editor at that language with the line "Reviewing. When you save, the request closes as edited by you."; the save carries `review: {id, requestId}`, and after the save succeeds the request closes as "edited". The notice's earlier versions (D102) keep both texts. A save from a request that is not the officer's, or already closed, still saves and leaves the request as it was.
- The notice's "Review" section lists the five newest answered requests ("PT · Approved by Rook · …", "All languages · Edited by Rook · …").
- Home's "To review" lists, above the screenshot drafts, one link per open request the officer may answer: "Review “Garden rota” · PT, asked by Ana".
- **The Home tab's number** (coordinator, 2026-11-17) counts these requests beside the screenshot drafts, on every page (`toReviewCount`): a request named for the viewer, or for the team when someone else asked. A request the viewer made does not count for them.
- **Recent activity** (D108): three lines from the same union read as the other small sources, with every name and title through `isolate()`. "Ana asked Rook to review the notice “X” · PT" (or "asked the team"), "Rook approved the notice “X” · PT", and "Rook edited the notice “X” after a review". A save from a request and its outcome share one instant, so the "edited after a review" line stands for the plain "saved the notice" line.
- Approval does not block Publish to Discord. Nothing is sent outside the app: no Discord message, no mail.
- The route answers 401 `signed_out` to no session or a member's session (D99, D105), and is in `member-session.test.ts`. Logs: `notices.review.asked` (whole 0/1), `notices.review.approved`.
- No comment or note field (owner, 2026-11-17).
